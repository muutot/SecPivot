# UI Language

Status: implemented (1.6) — `src/lib/i18n/` holds the `zh-CN` (source of
truth) and `en` dictionaries behind `t(locale, key, vars)`. The active
locale is the existing `general.language` setting (`"zh-CN"` default,
`"en"` opt-in); every component reads it from the settings store it
already subscribes to, so switching re-renders with no extra plumbing.

## Rules

- UI strings live in the dictionaries as flat dotted keys grouped by surface
  (`toolbar.*`, `settings.*`, `dialog.*`, …). Never hardcode a user-facing
  string in a component; never build user-facing text by concatenating
  translated fragments (word order differs per language).
- `en.ts` is typed `Record<I18nKey, string>`: adding a key to either side
  without the other fails `npm run check`. `tests/i18n.test.mjs` additionally
  asserts runtime key parity and non-empty values.
- Interpolation uses `{var}` placeholders via `t(locale, key, vars)`. When
  `vars.count === 1` and a `<key>_one` entry exists, it wins (English
  plurals; Chinese ignores it).
- Fallback chain is locale → zh-CN → the key itself: a missing translation
  degrades to Chinese, never to a blank.
- Code identifiers, comments, and commit messages stay in English.

## Known limitation

- Backend (Rust) error strings stay Chinese: they cross IPC as technical
  detail text, and plumbing a locale through every command would dwarf the
  UI migration. Revisit only with a backend locale contract (locale argument
  per command family or a session locale), plus round-trip tests.
