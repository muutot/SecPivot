# Security Model

KeyVault stores credentials in standard KDBX 4.0 files. This reference documents the security invariants the frontend and backend must preserve.

## Core invariants

- **Local-only**: the vault master password and the derived key never leave the machine. There is no telemetry or automatic upload. The one exception is the opt-in remote vault feature (S3 or WebDAV): opening or creating a remote vault sends the KDBX payload (encrypted with the master key) to the configured endpoint, and `save()` uploads it back. Local vaults never touch the network. Master passwords still never leave the machine — they cross the IPC to the backend only, and never to the remote storage.
- **In-memory session**: the decrypted database and the master password live only in backend managed state while a vault is open. `close_vault` and lock paths clear the session and zeroize the password buffer.
- **No persistence of secrets**: config (`config.json`) stores only preferences, never passwords or vault content. The browser demo fallback stores fake demo data only.
- **Clipboard hygiene**: copying a password schedules an automatic clear after `clipboardClearSeconds` (0 disables). The timer is reset on each copy and skipped when the user copies other content afterward. Lock clears the clipboard when `clearOnLock` is enabled.
- **No secret logging**: password and vault content must never be written to logs, debug output, or error strings.
- **Passwords never reach the frontend**: `VaultState`/`VaultEntry` carry no entry passwords in the Tauri runtime. Reveal/copy, editor prefill, CSV export, and the security report resolve secrets server-side (`get_entry_password`, `export_csv`, `security_report`) so plaintext crosses the IPC only on explicit user action. The browser demo fallback keeps fake passwords in `VaultEntry.password` for its local simulation only.
  **Browser bridge (KeePassHttp, opt-in)**: when `bridge.enabled` is set, a loopback HTTP server listens on `127.0.0.1:19455` only — never a non-loopback interface — and serves the KeePassHttp protocol (`associate`/`test-associate`/`get-logins`/`set-login`/`get-logins-count`/`generate-password`). Association keys live in the vault session (like keyfile bytes) and are wiped on lock/close; nothing bridge-related is persisted to `config.json`. Each response carries a fresh random `Nonce` used as the AES-CBC IV; sensitive fields (`Url`/`SubmitUrl`/`Login`/`Password`/`Uuid`/`Realm`/`Names[]`) are encrypted per-field with AES-256-CBC + PKCS7 and the whole response is authenticated by HMAC-SHA256. A first-time `associate` blocks up to 120 s for explicit user approval through a frontend event (`bridge-associate-request`, payload `{ token, id }` 鈥?never keys) answered by the `bridge_approve` command; unanswered requests are rejected on timeout. A locked vault answers with a plain error envelope and never triggers auto-unlock. Server-side, no decrypted plaintext is ever logged; errors in `bridge_server` are HTTP-status-agnostic envelopes. Design fact: `handle_request` runs under the `VaultSession` mutex, so an in-flight approval holds the session lock until it times out (120 s max) 鈥?one browser client can therefore stall other vault commands while its approval is pending.
- **KeePassRPC (Phase 2, opt-in)**: when the KeePassRPC server is enabled, a loopback WebSocket server listens on `127.0.0.1:12546` only and speaks the KeePassRPC protocol (SRP-6a setup 鈫?AES-256-CBC + HMAC-SHA1 JSON-RPC frames). SRP-derived session keys are held in the vault session per client username (like `bridge_keys`/keyfile bytes) and wiped on lock/close; nothing RPC-related persists to `config.json`. A fresh SRP handshake shows the randomly generated side-channel password only in the desktop UI (user types it into the browser extension) 鈥?it is never logged and expires with the pending handshake (120 s). Key-auth challenges (`cr`/`sr`) are SHA-256 over the session key. A locked vault answers with an error envelope and never auto-unlocks; a failed auth tells the client `AUTH_FAILED` so it drops its stored key and falls back to SRP. Non-WebSocket requests fail the handshake with the library's HTTP 400; valid WS handshakes to a path other than `/` get 404 (availability probe). Server-side, no decrypted plaintext or session key is ever logged.

## Lock lifecycle

Lock happens on:

- explicit lock action (`close_vault`);
- idle timeout when `autoLockMinutes > 0` (timer refreshed on `pointerdown`/`keydown`/`mousemove`/`wheel`/`scroll`, re-armed at most once per 15 s to avoid churn, reset on vault open, skipped when 0 or no vault open);
- `lockAfterAction` immediately after a password copy;
- focus loss when `lockOnFocusLoss` is enabled (installed from `+layout.svelte` via `installFocusLock`; locks only while a vault is open).

The frontend lock path (`lockVault` in `src/lib/services/security.ts`) zeroizes the session by calling `vault.close()`, and clears the clipboard first when `clearOnLock` is enabled. Password copies go through `copySensitive` so `lockAfterAction` applies only to the password, not usernames/URLs/notes.

After lock, the frontend `vault` store is cleared and the UI shows the lock screen (`LockScreen.svelte`) when a last-database path is remembered (`rememberLastDatabase`); otherwise it returns to the welcome screen. The remembered path (`vault.remembered`) is set on open/create and cleared only via "use another database"; the password is never persisted or remembered.

With `minimizeToTray` on (default), closing the main window does **not** lock — it merely hides to the system tray, keeping the in-memory session alive. Use the tray "锁定数据库" menu (or any lock path above) to drop the session; "退出" quits and fully ends the process.

## KeePass strengths

The `keepass` crate handles KDF (Argon2id/Argon2/AES-KDF), cipher (AES-256/ChaCha20), and compression. Defaults favor Argon2id + AES-256 + Gzip. Customizing these only affects newly created databases.

## Password generation

`src/lib/utils/password.ts` generates passwords from the configured charsets. It uses `crypto.getRandomValues`. Entropy is estimated as `length 脳 log2(poolSize)`; strength buckets are `<40` weak, `<72` fair, else strong. Similar/ambiguous exclusion filters `Il1O0` and `{}[]()/\\'"`~,;:.<>` respectively.

## Threat notes / accepted trade-offs

- Keyfile unlock is supported as a second factor: the keyfile path is user-picked, its bytes are read and kept in the session for save, and cleared on close. Keyfile contents never enter config, logs, or the frontend.
- Windows Hello quick unlock: when `rememberPassword` is enabled, the master password is stored in the OS credential store (Windows Credential Manager via `keyring`, DPAPI-protected per user) keyed by vault path. The lock screen probes `get_saved_credential` and offers a one-click unlock; the credential is removed on lock whenever the setting is disabled. This is the standard KeePass trade-off: the credential manager protects the password at rest, but anyone who can read the logged-in user's credential store can also unlock the vault. Hardware challenge-response (e.g. YubiKey) remains on the roadmap.
- **One-time passwords (opt-in per entry)**: seeds live only inside the vault session; `totp_code` returns codes, never seeds. TOTP (`otp`/`TimeOtp`), HOTP (`HmacOtp`) and Steam Guard (`SteamOtp`/`steam`) seeds are recognized; HOTP advances its counter on every code request and rewrites the `HmacOtp` field server-side *without* a history snapshot (showing a code must not pollute history), leaving the vault dirty so the next explicit save persists the counter — a code request therefore mutates the entry. The browser fallback computes TOTP only (UI surface, not desktop evidence).
- CSV export writes plaintext credentials (including passwords and TOTP seeds) to a user-chosen file via the save dialog and the `export_csv` command; the user must keep that file as secure as the vault itself. The security report analyzes empty/weak/duplicate passwords entirely server-side — only counts, uuids, and entropy bits cross the IPC.
- Auto-type replays entry fields as keystrokes via `enigo`; fields are resolved server-side from the vault session (the frontend never sends the password in the `auto_type` payload), a 300 ms grace period lets the user focus the target window, and execution runs on a background thread. The sequence itself may still be observed by other applications on the same machine 鈥?an accepted trade-off of the feature.
- **Remote vault credentials (opt-in)**: S3 access keys / WebDAV username+password are encrypted at rest with Windows DPAPI (`CryptProtectData`, current-user scope) and persisted as `dpapi1:<base64>` in `config.json`; legacy plaintext values are still accepted on read and re-encrypted on the next save. They are a secondary credential, never a vault master password 鈥?anyone who reads the config on the same user session can still use the storage, but the credentials are no longer readable as text from the file. Non-Windows platforms keep plaintext (no OS key store wired). Risk mitigations: credentials never appear in logs, remote commands resolve the profile from `ConfigStore` server-side (the frontend only sends the profile index, so credentials never cross the IPC for list/open/create), transport uses HTTPS (or the user's configured MinIO/WebDAV endpoint), and the payload is already encrypted KDBX. Local mirror copies ("保存到本地" mode) live under `<app_data>/Storage/remote/<sanitized>/` at rest with the same KDBX encryption. Threat model note: DPAPI protects the config only against offline file reads by other users/accounts; a process running in the same user session can still decrypt it.
- Screen-capture guard (opt-in, default off): when `security.screenCaptureGuard` is enabled, opening or creating a vault (local or remote) applies `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` (Windows 10 2004+; Windows only) to the main window so screenshots, recordings and screen sharing omit it, while the window stays fully visible on screen. The toggle lives on the welcome page and persists in config; the backend reads the setting at open/create time. `WDA_MONITOR` must never be used here 鈥?it renders the window as a solid black box on the physical display (black-screen bug) and, on some WebView2 builds, caused the main window to vanish entirely after unlock; the guard defaults off precisely to keep this class of issues away from users who did not ask for it. The guard is released on lock/close. TCATO overlay windows and the lock screen are not guarded (no secrets rendered there).
- The WebView clipboard write relies on platform clipboard; scheduled clearing uses a timer and cannot guarantee clearing if the process exits before the timer fires.

## Verification for security changes

- Targeted tests for lock/clear/session semantics (Rust).
- Confirm no password reaches `config.json`, logs, or the `VaultState`/`VaultEntry` payload by construction and test.
- Browser fallback changes are UI-only; do not claim desktop security behavior from them.
