# Data Contracts

This reference defines the frontend ↔ backend contract. Update it together with any change to IPC commands, serde types, config schema, or vault serialization.

## Config contract

`config.rs` persists `conf/config.json` beside the executable/project. The Rust `AppConfig` serde shape mirrors the frontend `AppSettings` (`src/lib/types/settings.ts`):

| Rust field       | TypeScript         | Notes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ---------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `general`        | `GeneralSettings`  | `language`, `theme`, `themeColors`, `customPresets`, `compactMode`, `density{groupGap,groupPaddingY,groupIndent,groupRadius,showGroupIcon,showGroupChevron}`, `showDescriptions`, `fontSizes{base,secondary,cardTitle,cardPreview}`, `windowEffect`, `windowOpacity`, `rememberLastDatabase`, `recentFiles` (max 8, trimmed/deduped on both sides), `windowWidth`/`windowHeight` (remembered main-window size, clamped 560–2560 / 420–1600), `panelWidths{group,detail,urlCol}` (drag-resized main panes, clamped 140–320 / 260–640 / 30–400; `urlCol` floor = header chars × 10px + 10px), `globalAutoTypeShortcut` (global auto-type hotkey, accelerator syntax like `Ctrl+Shift+A`, empty = disabled; passed verbatim, no clamp) |
| `security`       | `SecuritySettings` | `autoLockMinutes`, `clipboardClearSeconds`, `minimizeToTray`, `clearOnLock`, `lockAfterAction`, `lockOnFocusLoss`, `rememberPassword` (Windows Hello credential store), `screenCaptureGuard` (default `false`; when on, the main window is excluded from screenshots/recordings via `WDA_EXCLUDEFROMCAPTURE` while a vault is open — see `security-model.md` for the `WDA_MONITOR` black-screen pitfall)                                                                                                                                                                                                                                                                                                                            |
| `database`       | `DatabaseDefaults` | `kdf` (`Argon2id`/`Argon2`/`Aes`), `cipher` (`Aes256`/`ChaCha20`), `compression` (`None`/`Gzip`), `generator{length,includeUpper,includeLower,includeDigits,includeSymbols,excludeSimilar,excludeAmbiguous}`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

| `remote`         | (legacy)           | Single-profile shape written by pre-profile configs. | `rpc`            | `RpcSettings`      | `enabled` (default `false`; starts/stops the KeePassRPC loopback server via `set_config` and at startup, mirroring `bridge`). - `get_config() -> AppConfig`: read + normalize; returns defaults on first run.
- `set_config(config: AppConfig) -> AppConfig`: normalize + atomic save; returns the normalized value.

Frontend normalization lives in `services/settings.ts::normalizeSettings`; the backend must apply the same range/default rules so the round-trip is idempotent. New settings fields require both sides plus tests.

> **Pitfall — serde silently drops unknown fields.** The Rust `AppConfig` structs have no `deny_unknown_fields`, so a frontend field missing from the Rust serde shape is quietly discarded on `set_config`, written to disk, and returned as absent — the UI keeps it in memory via the fallback, but it **resets on the next launch**. Symptom: "my settings don't stick after restart", especially per-sub-item values while a parent toggle (e.g. `compactMode`) persists. Every new settings field must be mirrored in: TypeScript type + defaults + `normalizeSettings` (frontend), Rust serde struct + `Default` + `normalize_config` clamp (backend), and this table. The regression test `density_survives_deserialize_write_reload` guards the round-trip.

> **Pitfall — the read side: missing fields must not crash load.** Deserialization is strict by default: a required field absent from an existing `config.json` (old version, manual edit) makes `ConfigStore::load` fail, which propagates from the setup hook and **panics the app on startup**. Settings structs therefore use container-level `#[serde(default)]` (every struct also impls `Default`), so older files load with defaults for missing fields and `normalize_config` heals them. Exception: `AppConfig` itself uses **per-field** `#[serde(default)]`, because container-level `default` fills missing keys from `AppConfig::default()` — the seeded `remoteProfiles` would shadow the legacy `remote` key and block its migration. When adding a field, keep the `Default` impl updated and add a test loading a config without the new field. Guarded by `old_config_without_density_loads_with_defaults`, `empty_config_object_loads_with_defaults`, and `legacy_single_remote_migrates_into_first_profile`.

## Vault IPC contract

The vault session is held in backend managed state and returned to the frontend as serialized `VaultState`.

### Shared types (Rust serde ↔ `src/lib/types/vault.ts`)

| Type             | Fields                                                                                                                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VaultEntry`     | `uuid`, `groupUuid`, `title`, `username`, `password?` (browser demo only, never in the Tauri runtime), `url`, `notes`, `totp?`, `icon?`, `created?`, `modified?`, `tags?`, `favorite: bool` |
| `VaultGroup`     | `uuid`, `parentUuid` (null for root), `name`, `icon?`, `children: VaultGroup[]`, `entries: VaultEntry[]`                                                                                    |
| `VaultState`     | `path`, `fileName`, `root: VaultGroup`, `dirty: bool`, `modifiedAt`                                                                                                                         |
| `SecurityReport` | `total: number`, `empty: string[]`, `weak: WeakEntry[]`, `duplicates: DuplicatePasswords[]` (server-side analysis; no passwords leave the session)                                          |

`WeakEntry` = `{ uuid, bits }`; `DuplicatePasswords` = `{ count, uuids }`.

`EntryPatch` (batch edit payload) = optional `title`, `username`, `password`, `url`, `notes`, `totp` (empty string clears the seed), `expires` (empty string clears the expiry), `icon`, `color` (empty string clears the tag) plus boolean `clearExpires` / `clearIcon` / `clearColor`. An absent field leaves every target entry untouched — passwords are never fetched or re-sent for unchanged fields. camelCase both sides (`clearExpires` ↔ `clear_expires`).

The root group is the virtual top-level (uuid `"root"`); it is not persisted as a KeePass group — its `children` map to top-level groups and its `entries` map to the DB root group entries.

Every mutating command returns the refreshed `VaultState` so the frontend `vault` store stays in sync with the backend session. `favorite` is always present on `VaultEntry` and is persisted as a custom field `KeyVault.Favorite = "true"` (absent when not pinned); the browser fallback mirrors the same boolean on the demo state. `totp_code` is read-only: it computes the current one-time code via `keepass::db::TOTP` (`TotpCode { code, validFor, period }`), accepting either an `otpauth://` URI or a raw Base32 key (wrapped with SHA-1 / 6 digits / 30s defaults). The frontend `TotpWidget` counts down locally and refetches at each period boundary.

`auto_type` follows the KeePass sequence syntax (implemented in `src-tauri/src/autotype.rs`): placeholders `{USERNAME}` `{PASSWORD}` `{TITLE}` `{URL}` `{NOTES}`, special keys `{TAB}` `{ENTER}` `{SPACE}` `{BACKSPACE}` `{DELETE}` `{ESC}` `{UP}` `{DOWN}` `{LEFT}` `{RIGHT}` `{HOME}` `{END}` `{PAGEUP}` `{PAGEDOWN}`, `{{`/`}}` escapes, and literal text. Parsing is pure and unit-tested; keystrokes are replayed via `enigo` 0.6 (`Keyboard::text`/`key`) after a 300 ms grace period on a spawned thread, so the frontend gets the error only if parsing fails — execution failures are logged. The browser fallback rejects `autoType` with a dedicated message.

Global auto-type hotkey (`general.globalAutoTypeShortcut`): `src-tauri/src/lib.rs` registers the accelerator via `tauri-plugin-global-shortcut` at startup and re-registers on every `set_config`. On press, `src-tauri/src/focus.rs` reads the foreground window title (Win32 `GetForegroundWindow`/`GetWindowTextW`, Windows-only, returns `None` elsewhere) and `VaultSession::autotype_match` picks the best entry: URL host contained in the window title scores 2, entry title contained scores 1; the recycle bin subtree is skipped; the winner is replayed with the fixed sequence `{USERNAME}{TAB}{PASSWORD}{ENTER}` on a background thread. No match (or locked vault) logs and returns silently.

Field references: `VaultSession::expand_autotype_sequence` resolves `{REF:<Field>@<SearchIn>:<Text>}` (case-insensitive names, substring matching, `I` tolerates missing dashes, `O` matches custom string names) against the whole database except the recycle bin before parsing; unresolved refs abort with `字段引用未找到匹配条目`. Used by the `auto_type` command; the pure parser lives in `autotype.rs::expand_refs` (unit-tested) with the per-entry resolution in `vault.rs`.

TCATO overlay (two-channel auto-type, Windows-oriented): `open_tcato_overlay(uuid)` creates/focuses an always-on-top 360×190 window (label `tcato`) that loads the same SPA with a `#/tcato` hash — `src/routes/+page.svelte` renders `TcatoOverlay.svelte` in that mode. The overlay holds only the entry UUID (`TcatoTarget` state) and `tcato_state()` exposes title + `hasPassword` (never the password). `tcato_send(channel)` reads the field from the vault session and `focus::send_text_to_foreground` injects it into the foreground window via `WM_CHAR` messages (not visible to keyboard hooks); non-Windows falls back to simulated typing. `close_tcato_overlay()` closes the window. No real-window runtime evidence exists in this environment; the channel resolution is code-reviewed only.

Keyfile support (`open_vault`/`create_vault` `keyfile` arg): the user picks the keyfile path via the dialog; the backend reads the file bytes, builds the composite `DatabaseKey` (`with_keyfile`), and keeps the raw bytes in the session for re-save, clearing them on `close_vault`. Keyfile formats (XML `<Key><Data>`, 32/64-byte binary, hex) are parsed by the `keepass` crate at key-element time. A passwordless vault is allowed only when a keyfile is present. The browser fallback ignores keyfiles (demo data only).

### Remote vaults (S3)

`src-tauri/src/remote.rs` defines the `RemoteStorage` trait (`list`/`get`/`put`) with two implementations: `S3Storage` (rust-s3 0.34, path-style, custom `Region::Custom` endpoint so MinIO works) and `MemoryStorage` (Arc<RwLock<HashMap>>) used by offline tests. A remote session holds `Arc<dyn RemoteStorage>` plus `RemoteMode` (`InMemory` = upload back only; `SaveLocal` = also mirror locally) and `backup_count`. The display path is `s3://<key>`; remote paths are excluded from recent files and the lock-screen reopen flow (they need the S3 browser, not a local open).

- **Local mirror layout**: `local_storage_dir(app, cfg.local_dir)` → `<app_data>/Storage/remote/<sanitized>`. The sanitizer keeps only ASCII alphanumerics/`-`/`_` (other chars become `_`; empty → `remote`), so the user-defined directory cannot escape the tree. Saving writes `{name}.kdbx`, rotates the previous file to `{stem}.{timestamp}.{ext}.bak` (chrono `%Y%m%d%H%M%S%.3f`), and prunes to `backupCount` (0 disables).
- **Credentials travel per command**: each command builds a fresh `S3Storage` from the `cfg` argument sent by the frontend (which reads `appSettings.remote`); nothing is cached in the session.
- **`save()` on a remote session** serializes the DB, `put`s it back to S3, and — in `SaveLocal` mode — additionally writes the local mirror + rotates backups.
- **Bounded timeouts** (rust-s3 has only a connect timeout, never an overall one): `S3Storage` sets a 15 s connect timeout (`with_request_timeout`) and wraps each call in `tokio::time::timeout` — 30 s for `list`, 120 s for `get`/`put`. Failures surface as `S3 列表请求超时，请检查网络与服务地址` (etc.) instead of a UI stuck on "正在加载…".
- **Blocking off the async workers**: `S3Storage`'s sync methods `block_on` their own runtime, which panics on tokio worker threads — the command future aborts and the invoke never resolves (UI stuck on "正在加载…", refresh disabled, no error). Async commands therefore hop to the blocking pool first: `s3_list_objects` delegates to `remote::list_objects_async`; the open/create commands wrap `prepare_remote_open`/`prepare_remote_create` in `tauri::async_runtime::spawn_blocking` (the `Arc<dyn RemoteStorage>` is cloned for the closure; the password string is moved in, returned, and zeroized after adoption).
- The S3 transport is covered by offline `MemoryStorage` tests (open/save round-trip, mirror + rotation, invalid key/mode, create→save→reopen, close) **plus** an HTTP-level round trip against a local mock S3 server (`remote::tests::s3_transport_round_trips_against_local_mock` — path-style signing, ListObjectsV2 XML parsing, get/put) and a bounded-timeout test (`s3_list_surfaces_timeout_error_instead_of_hanging`). No live AWS/MinIO E2E evidence exists in this environment; real-provider behavior is still code-reviewed only.

### Browser bridge (KeePassHttp)

Split across two modules: `src-tauri/src/bridge.rs` owns the pure protocol (request/response types, per-field AES-256-CBC+PKCS7 encryption, verifier, response HMAC, request dispatch) and `src-tauri/src/bridge_server.rs` owns the loopback HTTP server, lifecycle (`BridgeState` managed state, started/stopped by `sync_bridge` on startup and every `set_config`), and the associate approval board (`ApprovalBoard` + `bridge_approve` command). The `BridgeHost` trait (implemented by `VaultSession`) isolates session access so the protocol layer is unit-testable without sockets.

- **Transport**: one JSON POST per TCP connection to `127.0.0.1:19455`; headers capped at 16 KiB, body at 1 MiB, read timeout 10 s. The server holds no secrets — a locked vault answers with `{"Success":false,...}` and no auto-unlock.
- **Associate flow**: browser sends `associate`; the server registers a one-shot approval token, emits the Tauri event `bridge-associate-request` (payload `AssociateRequest { token, id }`, never key material) to the frontend `BridgeApprovalPrompt` (mounted in `+layout.svelte`), and blocks up to 120 s for `bridge_approve`. On approval the client gets `{ Id, Key, Hash, Verifier, Success }`; keys are held in the session (`bridge_keys`) and wiped by `close_vault`. Re-associate with a known id refreshes that client's key.
- **Matching**: `get-logins` uses `url_host` host-equal-or-subdomain matching against entry URLs (same rule family as auto-type; the recycle bin subtree is skipped); entries carry `Uuid` (hex), `Login`/`Password`/`Url`/`SubmitUrl` encrypted, `Name`, `Realm` (empty), and `Totp?` when present. `set-login` updates an existing matched entry or creates one titled by the URL host. `get-logins-count` counts matches without payloads. `generate-password` returns a fresh 20-char password (upper/lower/digits/symbols, one per category — mirrors the app's `DEFAULT_DATABASE_SETTINGS.generator`) in the plaintext `Password` response field: it is newly generated for the browser to fill a form, not a vault secret, so it is not field-encrypted (still HMAC-authenticated via the response envelope).
- **`db_hash`**: SHA1 of (root group uuid ‖ recycle-bin group uuid) rendered as 40 lowercase hex chars — it changes whenever the vault structure changes, so browsers re-ask on identity changes.
- **Verifier/HMAC**: per KeePassHttp, the request `Verifier` = AES-256-CBC(key, iv = request nonce bytes) encrypting the base64 string of those nonce bytes — the server decrypts it and compares against `base64(nonce)`. Every response carries a fresh random `Nonce` (used as the AES-CBC IV for its encrypted fields) and `Hmac` = HMAC-SHA256(key, response `Nonce` bytes ‖ response `Verifier` ciphertext bytes); a fresh `Verifier` is likewise derived under the new nonce. Both sides validate accordingly. Tests cover NIST SP 800-38A block 1, RFC 4231 case 2, tamper rejection, and encrypted round-trips (offline; no real-browser E2E evidence in this environment).

Outside Tauri, `services/vault.ts` simulates the same commands on `demo-vault.ts` data persisted to `localStorage`. It is a UI-development surface only and must never be used as evidence for desktop KDBX behavior.

### KeePassRPC bridge (Kee 4.x)

Split across `src-tauri/src/rpc.rs` (pure protocol: SRP-6a math, key-auth challenge/response, AES-256-CBC + SHA-1 MAC frame crypto, v1 JSON-RPC method dispatch) and `src-tauri/src/rpc_server.rs` (loopback WebSocket server on `127.0.0.1:12546`, `RpcState` lifecycle started/stopped by `sync_rpc` on startup and every `set_config`, per-connection handshake state machine). The `RpcHost` trait (implemented by `VaultSession`, keys in `rpc_keys`, wiped on lock) isolates session access so the protocol layer is unit-testable without sockets.

- **Transport**: WebSocket upgrade required; valid handshakes to any path other than `/` get 404, non-upgrade HTTP gets the library's 400. Handshake steps use a 30 s read timeout, authenticated connections 300 s idle. Payload cap 1 MiB.
- **SRP-6a setup**: client sends `{protocol:"setup", srp:{stage:"identifyToServer", I, A}}`; the server generates a one-time side-channel password (8 random bytes as 16 lowercase hex chars, 120 s TTL), emits the Tauri event `rpc-side-channel-request` (payload `SideChannelRequest { password, expiresInSecs }` — shown in the desktop UI only via `RpcSideChannelPrompt` in `+layout.svelte`, never logged or persisted) and replies `identifyToClient {s, B, securityLevel}` with `features`. The proof exchange (`proofToServer` M / `proofToClient` M2) follows SRP-6a (1024-bit group); on success the derived session key (K = H(S)) is registered under the client username via `register_rpc_key` and mirrored per-connection. Error envelope codes: `AUTH_FAILED` (wrong password or vault locked), `AUTH_EXPIRED` (side-channel password expired).
- **Stored-key setup** (`key:{username}` → `key:{sc}` → `key:{cc,cr}` → `key:{sr}`): served only while the session key still exists; after lock the key is gone, so the server answers `AUTH_RESTART` and the client clears its stored key and re-SRPs. `cr`/`sr` = SHA-256 over `"1"|secret|sc|cc` / `"0"|secret|sc|cc`.
- **JSON-RPC frames**: `{protocol:"jsonrpc", jsonrpc:{message,iv,hmac}}` with AES-256-CBC (fresh IV) and the protocol's naive MAC `base64(SHA-1(SHA-1(key)||ct||iv))`. Requests are dispatched through `rpc::handle_jsonrpc` (GetAllDatabases, FindLogins, AddLogin, UpdateLogin, GetPasswordProfiles, GeneratePassword) under the `VaultSession` lock, never held across network I/O; responses are JSON-RPC 2.0 with numeric `id` echo. Tampered frames or a key wiped by lock close the connection without a reply.
- **Write path** (`AddLogin`/`UpdateLogin`, mirroring KeePassRPC `KeePassRPCService.JSONRPC.cs` + `MergeEntries`/`MergeInNewURLs`): `AddLogin [EntryDTO, parentUUID, dbFileName]` creates an entry (uuid server-generated) under the parent group (empty/unresolvable → root; a parent inside the recycle bin is skipped); `UpdateLogin [EntryDTO, oldLoginUUID, urlMergeMode, dbFileName]` requires non-empty `oldLoginUUID`/`dbFileName` and updates in place with a history snapshot (the plugin's `CreateBackup`), rejecting entries in the recycle bin. Field mapping follows `setPwEntryFromEntry`: first `FFTpassword` → `Password`, all `FFTusername` → `UserName` (last wins), remaining fields → custom strings named `displayName` (fallback `name`); `uRLs[0]` → `URL`, extra URLs space-joined into the same field so the read path sees every URL. URL merging (`merge_urls`) implements all five `urlMergeMode` modes (1 merge-new-first, 2 delete-old-primary-then-merge, 3 keep-old-append-new, 4 unchanged, 5 whole-list replace; unknown → 4); the server offers `KPRPC_FEATURE_ENTRY_URL_REPLACEMENT` so Kee sends mode 5. Responses are the updated entry DTO with an embedded `db` summary. Errors: `-32001` "oldLoginUUID could not be resolved to an existing entry.", `-32002` "Entry is in the Recycle Bin.", `-32600` for the plugin's `ArgumentException` mirrors. (Deviation: extra fields are stored as KDBX strings rather than the plugin's private "KPRPC JSON" config; the update path overwrites fields but does not delete stale custom fields.)
- **Locked vault**: SRP refused (`AUTH_FAILED`), stored keys absent (`AUTH_RESTART`), in-session JSON-RPC closes — the bridge never serves data while locked and never auto-unlocks.
- Offline verification only: protocol state machines are tested with the extension's own `SRPc` math (JS-mirror client) and raw-socket WS handshake/framing smoke tests; no real Kee 4.x E2E evidence exists in this environment.

## Serialization rules

- KDBX entry/group uuids are rendered as hex strings; group UUIDs are stable for the session.
- `password` never enters `VaultState` or the Tauri `VaultEntry` payload; reveal, copy, edit-prefill, CSV export, and the security report resolve entry passwords server-side (`get_entry_password`, `export_csv`, `security_report`). The browser fallback keeps demo passwords in `VaultEntry.password` for its local simulation. Entry passwords never enter config, logs, or error strings.
- `modifiedAt` is refreshed on every mutation.

## Cross-cutting gates

- Command names, arg names, serde casing (camelCase), error strings, and tests must stay aligned across `invoke` calls and Rust handlers.
- A new mutation requires: Rust handler + test, frontend `vault.ts` method, UI wiring, and this reference update.
