# Data Contracts

`save_entry({sessionId: String, request: EntrySaveRequest}) -> EntrySaveResult`
owns single-entry editor creation and editing. `request.target` is explicitly
`{mode:"create"}` or `{mode:"edit",uuid}`; an omitted edit UUID or extra create
UUID rejects, never defaults to creation. `input` retains the full-field contract;
optional/null `autoType` and `flags` preserve their current values. Flag members
retain absent/null keep, empty-string clear and explicit-value set behavior.
The native candidate validates target, attachments, foreground and managed-policy
conflicts before writing, then applies content/Auto-Type/flags in one tracking
scope for edits, trims history and publishes one revision. A final snapshot error
restores the original database, dirty/revision/modified metadata and snapshot cache.
Creation returns its exact UUID with the masked state and creates no initial
history. Memory-only CRUD remains available after save degradation, like existing
editor commands; persistence retains its own writable gate. Standalone mutations
remain available for other callers, and edit-multi retains `update_entries`.
Renderer UUID/state publication requires the captured Symbol lifetime even after
remote replacement; a closed/replaced response rejects. The editor uses the
returned UUID for selection rather than comparing creation timestamps. Browser
preview applies one cloned draft and validates its targets/foreground, without
proving native history, KDBX or provider behavior. Native candidates temporarily
clone decrypted data within the session; no large-vault memory benchmark or
allocator-erasure guarantee is implied.

`EntrySaveRequest.websiteRules` is optional/nullable: missing/null keeps the
managed policy, `{mode:"clear"}` removes it, and `{mode:"set",rules:WebsiteRuleSet}`
replaces it (including an empty explicit no-match set). Unknown members and
malformed structures reject with a fixed message without echoing input values.
Create requests cannot combine the custom-field policy source with this patch.
Validation uses the effective OverrideURL after flags: adding rules rejects an
inherited nonempty override, explicitly clearing it in the same save is allowed,
and clearing rules permits a new override. Content, flags and policy share the
candidate, tracked history, revision and snapshot rollback above.

`EntryEditorDialog` owns a `WebsiteRulesDraft` across tab changes. An initial
presence hint triggers one untracked explicit-session read; failures keep save
disabled until retry or explicit removal. Latest-operation and disposal guards
prevent stale publication; save-state changes never reload the draft. No policy
baseline plus a final disabled draft omits the patch, including blank templates.
Templates resolve policy and every hidden value together before replacing the
draft; missing/null policy reads for a presence hint reject the whole prefill.
`WebsiteRulesPanel` is controlled metadata UI with host default, exact URL bytes,
128-row ceiling and visible override conflicts. Browser preview refuses explicit
policy changes before publishing any draft fields. Its isolated renderer fixture
uses synthetic read/session/save seams; native persistence is tested separately.

Native renderer state publication registers an addressed session's epoch at
admission, including valid explicit IDs not listed yet. Each admission after
disposal and each replacement uses a fresh Symbol identity, so failed re-admission
of an old ID cannot match earlier responses; no disposed-ID ledger is retained.
Completion reads the
current epoch without recreating a missing lifetime. A disposed owner rejects
with the existing no-open-database error; replacement epochs retain the current
snapshot instead of caching the old response or its icons. Remote replacement
uses the same captured epoch. `list_sessions` reads capture `topologyRevision`;
successful open/create/close/switch transitions invalidate older tab-list results.
Listed uncached sessions receive an initial epoch and remain activatable.
Successful backend `close_all_vaults` immediately clears renderer state, tabs and
session/icon/epoch caches before awaiting temp cleanup. Cleanup tokens retain
their existing retry behavior. Synthetic real-service regressions cover these
boundaries; IPC schemas/native persistence, secret getters and UI view guards
remain separate contracts.

Remote `secretKey`/`secret_key` is an opaque password or signing key: frontend
normalization, queued `set_config`, native normalization, protected persistence
and transport construction preserve every character, including edge whitespace.
Only the exact empty string keeps an existing stored credential; a whitespace-only
replacement is a new nonempty value. Endpoint/region/bucket/access-key/prefix/name
normalization remains unchanged, and stored credentials still cross IPC masked.
Frontend real-service and native encrypted-reload/Basic-wire tests cover synthetic
values; no real provider, mobile secret store or recovery of already-trimmed keys
is implied.

WebDAV `RemoteObject.key` is a logical Unicode path, not a percent-encoded URI.
`href_to_key(base_url, href) -> Result<String, String>` decodes each path segment
exactly once before the shared request builder encodes it. Literal plus and
percent-looking names retain their identity. Absolute/path-absolute hrefs and
encoded endpoint paths are supported; legacy base-relative strings retain their
existing interpretation. Query/fragment suffixes are excluded from the path.
Raw dot segments are checked before URL normalization. Invalid escapes,
UTF-8, encoded slash/control/dot segments, interior empty segments and absolute
paths outside the configured root reject the entire list with content-free errors.
Absolute href authorities still do not select the request destination. Direct
create/open keys and S3 keep their existing logical-key contract. Bounded loopback
list/GET/PUT/readback tests cover resource identity, not real provider compatibility.

WebDAV href/size/modified properties are read as complete simple XML values.
Text, CDATA and standard named/numeric references concatenate without per-event
trimming; comments/processing instructions do not erase preceding text. Reference
decoding is once per event, preserving literal entity-looking text. Trim only the
complete value, then apply the existing URI decoder or optional metadata parser.
Unknown references, invalid decoding and nested/truncated property content reject
the whole list with content-free errors. Missing/empty size/date hints and existing
collection handling remain. `tests/fixtures/webdav-xml-text.json` supplies eight
independent standard-XML controls; the native wire regression covers thirteen
filename classes. Namespace/context handling is described below; full XML,
propstat and provider compatibility remain separate. No IPC/schema/dependency
changes are involved.

WebDAV list publication additionally requires exactly one completed multistatus
document root. A second root, unclosed envelope, wrong-root error page or
non-whitespace outside the root fails with a content-free document error.
The envelope pass runs after property parsing, retaining existing field-specific
failures; it uses a streaming depth counter and does not publish partial objects.
Valid empty lists, case-compatible local tag names and surrounding XML whitespace,
comments and PI remain supported. The envelope pass alone does not validate
namespaces/propstat/full XML or resolve external entities. The shared strict-JSON
tests/fixtures/webdav-document-envelope.json supplies independent document controls.

WebDAV PROPFIND explicitly requests DAV:resourcetype alongside size/date, matching
the parser's collection filter. The request-driven native HTTP fixture excludes
non-slashed collections and keeps normal/extensionless files and metadata.
Unavailable type/size/date remain optional; filename extension or zero size is
never used to infer collection membership. Namespace/context handling is described
below; propstat/provider limits remain, with no IPC/schema/dependency change.

WebDAV uses NsReader expanded names and expected parent containers for responses,
href, propstat/prop metadata and resourcetype/collection. Unknown/unexpected
elements and their entire subtrees are ignored, including familiar DAV-looking
descendants. DAV prefix aliases/default namespaces and existing uppercase names
remain compatible. An entirely unqualified root selects a separate legacy mode;
unqualified children under a DAV root are not DAV fields. Non-DAV roots and
unbound prefixes reject without XML contents. Scalar errors remain content-free,
and namespace parsing does not resolve external entities. The strict-JSON
tests/fixtures/webdav-namespaces.json corpus covers sixteen independent controls.
Propstat success/duplicate/full XML/provider semantics remain separate.

Welcome local/remote open and create forms accept a password, a selected keyfile,
or both, matching native build_database_key and LockScreen. An empty password is
rejected only when no keyfile is selected; local creation still validates password confirmation. Keyfile
requests never remember a password-only credential. Existing backend keyfile
validation and IPC shapes are unchanged. tests/welcome-credentials.test.mjs
executes the four production handlers with synthetic service seams; native
keyfile-only create/change/reopen controls are separate from picker/provider proof.

The patched shared Argon2 transform rejects KDBX u64 iteration or byte-to-KiB
memory values that do not fit u32 instead of truncating them. Existing open/save
error contracts carry the failure; no IPC, config schema or default changes.
Native local/remote open keep the active session and avoid mirror creation on
these failures. Save serialization rejects before destination publication,
preserving the previous file. Two empty synthetic KDBX4 fixtures under
tests/fixtures/kdf-overflow-* reproduce the original reader/writer mismatch;
their provenance hashes identify the unpatched registry producer.

The KDBX internal XML writer represents raw CR as character references after
trusted text-only serialization, preserving CR/CRLF in ordinary field values/
keys, current/history versions and group/meta text. Literal entity text retains
its escaped spelling and protected fields retain their base64 ciphertext. The
reader keeps standard XML normalization for raw CR from other producers.
Entry StringValue explicitly deserializes `$text` through a direct String
converter, preserving ASCII and Unicode whitespace. The pinned QuickXML reader
retains blank events only for structs with a dedicated `$text` field; structural
maps and generic optional metadata keep their existing rules. Empty Value and
missing-Value rejection, protected Base64 and current/history semantics remain.
Original-registry fixture/XML provenance and native open/rewrite/current/history
regressions cover this boundary. Invalid XML scalars and group/meta whitespace
remain separate; this change does not recover already-lost content.

KDBX to_xml validates the XML 1.0 Char ranges on actual serialized text before
encrypted destination publication. Forbidden ordinary values/keys/group/meta
and history text fail with a content-free error, preserving the previous file
and live dirty edits. Protected Base64 keeps arbitrary underlying scalars;
TAB/LF/CR/NEL and allowed supplementary noncharacters retain their values.
Import remains lossless in memory; invalid historical ordinary text can also
prevent saving. The reader is unchanged and no automatic sanitization/recovery
or complete native-client compatibility is implied.

CSV export in `utils/csv.ts` and `vault/serialize.rs::escape_csv` adds the
existing formula guard apostrophe to the field value before RFC 4180 quoting.
Commas, quotes and CR/LF therefore remain within one cell. This preserves the
guarded value, not an exact original-value round trip: an inserted guard stays
in imported text and literal source apostrophes must not be stripped. Native
file and frontend wire regressions cover all six guarded prefixes and ordinary
quoted values; independent Python stdlib CSV reads corroborate their boundaries.

`parseCsv` preserves BOM-free text, quoted empty fields, escaped quotes and
embedded CR/LF; CRLF, LF and CR delimit records outside quotes. Malformed quote
placement, trailing text after a closing quote and unterminated quotes throw
`CsvParseError` before any rows return. `io.csvToImportEntries(text, language?)`
translates that content-free error with the current locale by default. The main
CSV handler catches it under the captured view and stops before group creation
or batch IPC. It also discards an obsolete picker completion before parsing.

The XML page handler likewise checks the captured view before conversion and
catches parser failures with localized content-free feedback before any group
or batch write. Its picker lists XML only; Android MIME fallbacks still cover
text/xml and generic provider text. Malformed and encrypted-field XML continue
to fail at the existing parser boundary, while stale picker results do not parse.

New-entry templates resolve all hidden password, OTP and protected-field values
atomically through `resolveTemplateSecrets`. Failed reads retain the draft and
show an error. Component destruction or a session/path change invalidates pending
template completion; the selector is create-only and blank resets template fields.
Recursive `GroupNode` instances forward both `templatesGroup` and `ontemplates`,
so nested group menus retain the set/unset label and dispatch the page callback.

Persistence returns `PersistOutcome { hash, mirror_warning }`: once the remote
upload commits, failure of its optional local mirror is a warning, never a failed
upload. Save, key change, settings rewrite, creation, merge and RPC completion
adopt the committed hash/key and expose `VaultState.mirrorWarning` (null clears it).
Even a stale merge completion advances the remote base while preserving live edits.

Remote OS-keyring field addresses include a hash of the canonical data root and
the full `kind/name` profile path. S3/WebDAV names and portable installations
cannot overwrite one another; legacy embedded keyring references still load and
are migrated to the scoped address on save. Windows DPAPI inline values are unchanged.

`io.pickSaveFile({defaultPath, filters?})` owns native destination selection for
CSV/XML/emergency HTML and both attachment-save entry points. Android uses
`saf.createDocument(fileName, mimeTypes?)`; desktop keeps plugin-dialog save.
Vault create/save-as keep the KDBX MIME default. The helper returns only the
selected path/URI and never remembers exports as recent vaults. Caller view
guards still run before backend secret extraction/write, and emergency HTML
captures `includePasswords` before selecting. Export/attachment IPC schemas and
session-id routing are unchanged. Their writers share `file_io::write_named`:
local paths use atomic replacement; mobile URIs reuse bounded old-content read,
write/readback verification and verified rollback, with file-specific errors.
Temporary export/attachment command buffers and URI readback/rollback buffers
use Zeroizing. Host tests do not prove native Android provider compatibility.

Text imports on Android select via `saf.openDocument(mimeTypes?)`, whose default
remains the KDBX MIME set for vault opening. Import filters include their format
MIME and plain-text/binary provider fallbacks. `read_text_file({path, fileName?})`
accepts an opaque document URI plus its provider display name; local paths always
validate their actual extension and ignore `fileName`. CSV/XML/JSON/1PIF are format
filters, not path authorization. Reads use `vault/file_io::read_with_limit` with
an 8 MiB streaming ceiling and strict UTF-8. Missing/unsupported document names
fail before reading. Picker and read completion both require the original view;
A→B→A after a picker opens cannot start an obsolete plaintext read. Native
provider behavior still needs Android APK/device verification.

`BridgeApprovalPrompt` captures the displayed request object before invoking
`bridge_approve`. Success, failure, busy cleanup and the dismissal callback apply
only while that exact request is current. Replacing a prompt or unmounting
invalidates old IPC completions; an old approval cannot mark or dismiss a new one.
This renderer guard does not replace backend token/session/lifetime validation.

Permanent entry/group deletion and recycle-bin emptying use EntryTrack/GroupTrack
remove, recording concrete DeletedObjects timestamps for every removed object,
including recursive descendants. Ordinary moves into the bin record no permanent
deletion. These UUID/time markers survive KDBX save/reopen and prevent untouched
stale copies from reintroducing deleted records. Genuinely newer content edits
retain the existing merge winner policy; deletion is not an unconditional veto.
Batch UUID validation precedes removals or tombstones. Untracked removal remains
appropriate for temporary merge detachment, which must not create user deletions.

EntryTrack drop explicitly collects released snapshot attachment IDs after
permanent removal has erased their reverse references. Collection requires no
remaining lease or recursive current/history owner. Other shared payloads and
preexisting unrelated orphan headers remain. Native single/batch/subtree and
recycled/empty-bin paths verify current/history removal through save/reopen and
surviving attachment bytes; dependency tests cover aliases and nested guards.
The separate merge finalization contract handles prepared imports.

prepare_attachment_merge returns an opaque in-memory AttachmentMergeState with
the prepared binary IDs and destination's original unreferenced header IDs.
complete_attachment_merge still installs source winners and releases preparation
leases without early collection. After equal/losing history union and local bin
restoration, finalize_attachment_merge validates no remaining leases or missing
recursive owner payloads and collects unowned prepared IDs. Original destination
orphan headers and binaries introduced after preparation remain. Source orphan
headers retain the existing exclusion. Actual deleted entry/subtree merges and
saved orphan-header fixtures cover both directions and repeated save/reopen;
existing history/bin/current winner tests protect late owners.

Patched native group merge decides each object's deletion independently. A newer
deep entry/group edit restores its required ancestors, while unchanged siblings
still follow their own markers. Group removals run child-first after all entry
and group moves and require emptiness; no ancestor removal cascades over a
survivor. Retained ancestors lose obsolete markers and Deleted log events cover
actual removals only. Equal/missing timestamps and content-before-location
fallback keep the existing policy; unknown deletion times remain asymmetric.
This is not a complete cross-client deletion-lifecycle guarantee.

After restoring the final local recycle bin, first-party merge unions both
original DeletedObjects maps for UUIDs absent from the final entry/group/custom
icon sets. It retains the latest concrete time (concrete supersedes unknown),
including objects both copies deleted and records the recipient never received.
Existing merge-generated markers also participate. Final active/bin/icon
survivors do not receive new markers through this union. Object winner rules,
existing survivor markers and local-bin collision semantics remain unchanged.
This prevents three-copy resurrection from dropped/older deletion metadata;
unreferenced attachment retention and physical erasure remain separate concerns.

`RpcSideChannelPrompt` dismisses and releases its pending password on expiry,
manual close and unmount. Its wall-clock countdown catches delayed timer callbacks
and refreshes on focus/visibility resume and before copy. Old timer/copy completions
must still own the same request object to update the UI. The event payload is
`{ requestId, password, expiresInSecs }`; `requestId` is a process-monotonic decimal
string, distinct from the connection id. `rpc-side-channel-ended` carries only
`{ requestId }` on subsequent setup (proof or replacement) and connection exit.
The renderer closes only the matching prompt and remembers the latest nonsecret
identity, rejecting old/duplicate shows and end-before-show delivery. A connection
owns a secret-free RAII prompt lease; its end callback never locks vault/lifetime
state. `vault/session_end.rs` provides weakly registered, nonsecret one-shot
signals ended centrally by successful active-vault transitions in `VaultSessions`.
The prompt registers under the active mutex; open/create adoption, active close,
lock and tab switch therefore end even idle prompts. Parked close, failed changes
and idempotent switch preserve them. Proof with an already-ended signal is refused,
including a return to the original stable tab id. No new IPC command is required.

KeePass XML export uses the official PlainXml value contract: escaped literal
text and `ProtectInMemory="True"`. Import decodes old unencrypted `Protected`
Base64 only when `Meta/Generator` identifies SecPivot, with strict UTF-8 validation;
foreign encrypted fields and mixed protection markers fail before any import writes.
Native `TimeOtp`, `HmacOtp`, `SteamOtp` and `steam` fields remain custom fields,
including their protected flags; only `otp` uses the dedicated input. XML export
writes actual OTP keys once and includes entry expiry. Browser export-row mapping
copies custom fields and expiry instead of reducing XML to the CSV field set.
XML export encodes CR as a character reference to preserve credentials through
XML newline normalization. Both writers reject characters outside XML 1.0's
Char production before destination I/O rather than deleting them. Browser
`buildKeePassXml(rows, lang?)` uses the UI locale for its content-free error
(default English for existing callers). Rust's intermediate document is
Zeroizing, including failure paths; returned command content retains the existing
zeroizing writer boundary. PlainXml still cannot represent every KDBX secret.

Structured Bitwarden import retains types 1–8 (login, secure note, card, identity,
SSH key, bank account, driver license and passport). Typed fields use protected,
source-prefixed unique custom names; unknown extension values retain JSON, and
malformed known string fields/unknown types reject the whole parse with a
content-free record number. `ImportRow.qualityCheck?` passes through
`io.importRowsToEntries`, `ImportEntry`, and `ImportEntryInput` to `import_entries`.
Rust flattens the ordinary `EntryInput` alongside optional `quality_check`;
the common batch insertion validates groups/attachments first and sets the flag
at creation. Bitwarden login enables quality evaluation, other types disable it;
absent metadata keeps the KeePass default (CSV/XML/1PIF unchanged). Browser bulk
fallback preserves the same flag. Ordinary full-field edits still preserve flags.
These are schema-based synthetic KDBX regressions, not native export validation.
Common name/notes/folderId and login username/password/totp values must be
strings when present and non-null. Missing/null optional values stay empty.
Login must be an object; folders/fields must be arrays with valid members.
Custom field names/values use the same string check, and present types must be
numeric 0–3. Missing legacy type remains Text; invalid metadata never becomes
an unprotected guess. Content-free errors reject the whole document before
rows return. Synthetic command/wire/KDBX tests preserve valid hidden/linked
masking and optional values; full source-format compatibility remains partial.
Linked type-3 fields resolve official login/card/identity IDs into protected
import-time snapshots through `import/bitwarden_links.rs`; Identity FullName
follows source name-part composition. Optional absent/null targets become empty
protected fields. Unknown/cross-type/non-integer IDs or malformed target values
reject the whole parse. Stale field.value never overrides the linked target.
Dynamic linkage after edits, URI matching modes, collections, native history and
attachments remain separate migration work.

Bitwarden URI import accepts at most one nonempty URI with absent/null `match`.
Explicit modes 0–5 and multiple nonempty URIs reject the entire parse with a
record-numbered compatibility error. Malformed array/object/string/mode shapes
and embedded whitespace reject as invalid rather than becoming native URL
destinations. Missing/null/empty URI collections remain valid. No partial rows
are returned or schema fields added; complete per-URI matching remains pending.

KPRPC empty allow/block regex expressions are ignored by the shared matcher,
including browser host adapters and auto-type scoring. Nonempty whitespace and
explicit wildcard patterns retain their meaning; existing compile/input limits
and malformed-regex handling are unchanged.

Native `update_entry_flags` validates the optional foreground color before
writing any matching/quality/color attribute. An invalid color leaves the raw
entry, cached snapshot, dirty flag and revision unchanged, including a later
save/reopen. Existing absent/empty/valid values and target-error order remain.

`update_entry_flags` and `update_entry_autotype` refresh the entry's
`Times.last_modification` with `Times::now()` when normalized attributes change,
so an old timestamp does not obstruct a standalone edit's merge. Repeated
equal values retain the timestamp. Their existing dirty/revision and history
behavior stays intact. The editor now uses `save_entry` for one complete pre-edit
snapshot instead of attribute follow-ups. This does not establish complete
history for every standalone attribute command.
Times retain KDBX second precision; same-second divergence is a separate
merge boundary, not a monotonic timestamp guarantee.

Group content edits (`rename_group`, `set_group_icon`, `update_group_meta`,
and `update_group_autotype`) likewise refresh `Times.last_modification` on
actual normalized changes, including root metadata and Auto-Type settings.
Equal values keep the group time. Auto-Type enabled omission intentionally
restores inheritance as the dialog requests; the sequence keeps its separate
omitted/empty behavior. This does not change group expansion or move timestamps.

Favorite toggles refresh the entry's second-precision modification time and
return its exact formatted time and computed total size in the Favorite
MutationDelta (`modified: String`, `size: u64`). The renderer patches favorite,
modified and size together, preserving immutable untouched tree nodes. The demo
fallback refreshes its local entry time; native size comes from the backend.
The existing dirty/revision and no-extra-history behavior stays intact.

Group tags in native merge use the pinned crate's actual Group Created/Updated
log events. keepass 0.13.22 omits tags in both branches; source-only group tags
are cleared only in the temporary source clone to avoid its immediate equal-time
check on incompletely copied new groups. After successful merge, surviving source
winners receive their original remote tags, including an empty set. Existing
same-time divergence remains an error; local winners, deletion and recycle-bin
exclusion keep their existing decisions. No vendored bytes are changed.

Bitwarden nonempty `passwordHistory` arrays are archived as a uniquely named,
protected `Bitwarden Password History` custom field. The source JSON preserves
order, duplicates, empty passwords, optional/null string dates and extra keys;
it does not invent complete native entry versions. Every record requires a
string password; invalid containers/records/date types reject the document
with the existing content-free indexed error. Missing/null/empty history adds
no field. Generic import custom-field IPC and native KDBX protection carry it.

The pinned keepass 0.13.22 package is locally patched for attachment ownership
and dense KDBX4 header references (see `src-tauri/vendor/KEEPASS_PATCH.md`).
Native merge prepares a shared attachment namespace in temporary database
clones before comparing entries or merging histories. Identity includes exact
bytes and the protection flag; SHA-256 only indexes equality candidates.
Created/Updated entry events select current binary references, then reverse
ownership is rebuilt after losing versions join history. Detached local recycle
bin entries restore every current/historical payload from the immutable local
input, with complete version-layout validation before copying maps. Missing
payloads reject the merge without publishing a partial database. The patched
Database methods are prepare_attachment_merge, complete_attachment_merge,
copy_entry_attachment_versions_from and rebuild_attachment_references.
Preparation rejects existing history/merge leases and leases all destination
binaries until actual winner ownership is installed. Entry removal respects
those leases and visits each binary ID once when multiple filenames share it.
The first-party merge wrapper separately unions source histories when current
modification times match. Local-winner source snapshots and history-only unions
deduplicate by timestamp plus content, including expiration and canonical
binary references; distinct same-time versions remain restorable. Timestamp
buckets limit comparisons to candidate duplicates. Repeated unions preserve
version count, and descending time order keeps newest-first history indices.
Patched History::from_entries builds the sorted list once and strips nested
history trees instead of repeatedly moving the growing list with add_entry.
Current-content divergence at an identical timestamp still rejects the merge;
this is not a complete cross-client merge compatibility guarantee.
LocationChanged and PreviousParentGroup follow the selected move independently
of LastModificationTime, even when both copies already have the same parent.
Current/previous parents do not identify content versions or history duplicates.
Cycle-safe group staging restores source previous-parent provenance after the
final move. An opaque previous-parent UUID may refer to a removed group; the
resolved previous_parent() helper returning None does not imply the UUID is lost.
Different-parent moves with missing location times retain destination provenance
and warn; they never stamp an unapplied source move onto the destination.
Expiration date/enabled are part of first-party version content. Older current
versions are captured in either merge direction, including expiration-only
changes. Actual Entry Created/Updated outcomes copy source expiration settings.
Equal-current-time expiration conflict candidates are captured before winner
timestamps change; surviving divergent entries reject after native deletion
decisions and before database publication or any persistence. Deleted objects
are never re-created by this metadata completion step.

Tracked edits lease old binaries until the pre-edit snapshot is appended;
deletion affects only the addressed entry version. History count/size trimming,
single-version deletion and clear-all reindex references and reclaim only
affected orphans. Loading reconstructs all reverse references without sweeping
unreferenced header payloads. Serialization maps every current/history Binary
Ref to the exact header order and rejects missing data before publication.
The three history helpers now accept `EntryMut`, enabling ownership reindexing;
the normal IPC contract is unchanged. `restore_entry_version` replaces the whole
attachment set as well as fields/attributes. It resolves binary Values before
mutation, preserving protection flags, and records the pre-restore attachment
set for undo; normal history retention still applies. No binary bytes enter the
history DTO. External attachment imports now use the same EntryTrack snapshot,
last-modified update and count/size retention path as ordinary attachment edits.
The session-bound temp reader and IPC schema are unchanged.

Native history retention uses nonnegative count/size limits exactly: zero
retains no snapshots, and negative values are unlimited. An absent count keeps
the KeePass default of ten; an absent size uses KeePass's 6 MiB byte budget.
The size budget may remove even the newest snapshot when it cannot fit. Cleanup runs on the
existing tracked mutation paths, reindexing attachment owners after trimming;
setting metadata alone does not eagerly purge all entries. Restore undo is
therefore conditional on the configured budget.

Main-window `flash(message, kind = "success")` forwards the existing TipKind.
IO/group/favicon/editor notification seams accept `(message, kind?: TipKind)`;
explicit failure branches pass `"error"`, while normal completion retains the
success default. Kinds are assigned at the branch, never inferred from translated
text. The existing TipsHost danger palette renders errors; view/busy guards and
backend result contracts remain unchanged.

Favorite import metadata is optional on `ImportRow`, `io.ImportEntry`, and
`ImportEntryInput`; the mapper and bulk IPC preserve it. Bitwarden accepts only
boolean `favorite` when present. The native batch validates every group/payload
before setting the existing `SecPivot.Favorite=true` field at creation; false/
absent keep the non-favorite default. Browser creation mirrors it. Ordinary
entry edits have no favorite input and preserve the current flag.
CSV recognizes an explicit Favorite header, including reordered columns. It
accepts case-insensitive true/false and numeric 1/0, with an empty cell meaning
unspecified; invalid cells fail the whole conversion with localized content-free
feedback. Legacy positional rows have no inferred favorite field. Own CSV
exports retain their header and true/false output; XML/1PIF behavior is unchanged.

## Config contract

Malformed config recovery reports only serde_json's category, line and column,
plus the existing backup/default-start status. Do not format the full parser
error: type errors can embed credential-field input values. Recovery retains
the corrupt file and loads defaults; valid input and masked IPC are unchanged.
The native regression captures actual child-process stderr and requires the
child fixture to execute; an immutable module probe separately checks the log.

`config.rs` persists `conf/config.json` under the data root resolved by `config::resolve_data_dir`: portable mode (a `portable.flag` marker or a legacy `conf/config.json` beside the executable) keeps everything next to the executable so the folder travels as one unit; otherwise the per-user app-data dir is used (installed builds must not write into `Program Files`). - `get_config() -> AppConfig`: read + normalize; returns defaults on first run. Remote credentials arrive **masked** (`accessKey`/`secretKey` blanked); presence is queryable via `remote_secret_present` without revealing values.
- `set_config(config: AppConfig) -> AppConfig`: normalize + atomic save; returns the normalized value **masked** (never a read-back oracle). Empty incoming credentials mean "keep the stored ones" (placeholder-keep merge by `<kind>/<name>` path); clearing happens by deleting the profile. Renaming a profile orphans its stored credentials (new identity) and the UI asks for re-entry.
- `remote_secret_present(profile: String) -> { accessKey: bool, secretKey: bool }`: presence flags for the placeholder UI.

Frontend normalization lives in `services/settings.ts::normalizeSettings`; the backend must apply the same range/default rules so the round-trip is idempotent. New settings fields require both sides plus tests.

> **Pitfall — serde silently drops unknown fields.** The Rust `AppConfig` structs have no `deny_unknown_fields`, so a frontend field missing from the Rust serde shape is quietly discarded on `set_config`, written to disk, and returned as absent — the UI keeps it in memory via the fallback, but it **resets on the next launch**. Symptom: "my settings don't stick after restart", especially per-sub-item values while a parent toggle (e.g. `toolbarItems`) persists. Every new settings field must be mirrored in: TypeScript type + defaults + `normalizeSettings` (frontend), Rust serde struct + `Default` + `normalize_config` clamp (backend), and this table. The regression test `density_survives_deserialize_write_reload` guards the round-trip.

> **Pitfall — the read side: missing fields must not crash load.** Deserialization is strict by default: a required field absent from an existing `config.json` (old version, manual edit) makes `ConfigStore::load` fail, which propagates from the setup hook and **panics the app on startup**. Settings structs therefore use container-level `#[serde(default)]` (every struct also impls `Default`), while `AppConfig` applies `#[serde(default)]` per field. When adding a field, keep the matching `Default` impl current and add a load test. Guarded by `old_config_without_density_loads_with_defaults` and `empty_config_object_loads_with_defaults`.

`ThemeColors` mirrors the frontend `ThemeColors` key-for-key and now includes `linkColor` (defaults: dark `#1e90ff`, light `#0066cc`; accent defaults dark `#8bc34a`/light `#689f38`, selection dark `#808080`/light `#757575`; normalized via `valid_hex`, missing keys fall back to the dark preset). A new theme color must be added on both sides (frontend `types/theme.ts` + `utils/theme.ts` map + `app.css` root default + settings picker in `GeneralSettingsPanel.svelte`, Rust `ThemeColors` struct + `dark()`/`light()` + `normalize_colors`) and covered by a round-trip test like `link_color_survives_deserialize_write_reload_and_old_configs_default`.

**Multi-session registry (tabs):** `src-tauri/src/vault/sessions.rs::VaultSessions` (managed state) parks every non-active session under a stable generated `sessionId` (`s1`, `s2`, …); the backend-active session always lives in the app's `Mutex<VaultSession>`. Opening/creating a vault parks the previous active session under its existing id and activates the new one, so several databases stay decrypted in memory at once. Every renderer-originated session command captures and sends `sessionId`; command wrappers route through `VaultSessions::with_session_mut` instead of assuming the backend-active slot (omission remains a compatibility fallback only). The frontend keeps a `VaultState`/custom-icon cache per session, rejects lower-revision late snapshots and every response from before a whole-session replacement (remote download epoch), and publishes results only while that id is still visible. Service methods return that actually committed cache state when a late raw response is rejected, and tab-list refresh retains a renderer active id only while the backend still lists it. Composite operations explicitly reuse their starting id, extracted attachment tokens are owner-bound in the backend store (not merely trusted from the renderer), TOTP cache keys include the session id, and session-scoped dialogs, menus, mobile drawers, selections, loaded secrets, status notices, and sensitive export choices are cleared on a tab change. The group tree is keyed by the session that owns the published `VaultState`, not merely the earlier active-id notification, so identical copied databases cannot reuse expansion, rename, or context-menu component state. Page-level long operations additionally capture a visible-session epoch: returning A after A→B starts a new epoch, so the first A view cannot reopen reports or clear `busy`/form-saving flags belonging to the new A view; latest-operation tokens also prevent older same-view completions from clearing a newer activity. Delayed expiry notices use the same epoch and are deduplicated by `sessionId:path`, preventing a previous tab from flashing after a switch while still allowing the browser demo's fixed `browser` id to open another path. The entry editor awaits the parent's complete create/edit/autotype/flags promise, blocks cancel/re-submit until it settles, and the parent applies close/selection/toast results only to the captured visible epoch. Native file dialogs capture that epoch before opening: import actions discard stale picker/read/parser results before any database write, and save-as discards a stale chosen path before `save_vault_as`; once an import starts, every group-creation iteration and the final batch insert explicitly reuse the original session id. `set_active_session` is idempotent and each complete frontend switch attempt (including an uncached tab's snapshot validation) is synchronously enqueued before any wait; validation failure therefore cannot leave the renderer restored to one tab while a previously queued backend swap later activates another, and rapid A→B→A requests finish in click order. Every renderer topology operation (`open`/`create`, remote open/create, close/close-tab/close-all, and tab switch) shares that same queue, so its backend registry mutation and matching frontend publish finish atomically in invocation order. Bridge/RPC/global-hotkey access remains intentionally limited to the backend-active session. Long prepare/persist/complete commands (`save_vault`, `save_vault_as`, `change_master_key`, `download_favicons`) carry the originating id through every phase; favicon progress and Auto-Type picker events also carry the owner id and are ignored by other tabs. `close_all_vaults` closes every session (the lock path), closing active promotes the last parked session, and the screen-capture guard stays on while any session remains open. Frontend behavior tests cover switch/topology ordering, invalid-active fallback, visible-epoch invalidation, failure and stale-state rejection, while the backend regression duplicates one KDBX so both tabs have identical entry UUIDs and proves an addressed mutation changes only the named session.

`CustomField` (in `VaultEntry`/`HistoryVersion`/`EntryInput`) = `{ name, value, protected: bool }`. In the Tauri runtime a protected field's snapshot `value` is **always empty** — the real value never leaves the session and is resolved on demand via `get_custom_field_value` (reveal, copy, and editor prefill); the `protected` flag itself is always serialized. Writes go through `update_custom_field` (one value at a time, protected flag carried by the caller so an inline edit never downgrades a protected field). Unprotected fields carry their value in the snapshot as before. The browser demo fallback keeps protected values inline for its local simulation only.

`EntryPatch` (batch edit payload) = optional `title`, `username`, `password`, `url`, `notes`, `totp` (empty string clears the seed), `expires` (empty string clears the expiry), `icon`, `color` (empty string clears the tag), `tags` (empty string clears the tags) plus boolean `clearExpires` / `clearIcon` / `clearColor`. An absent field leaves every target entry untouched — passwords are never fetched or re-sent for unchanged fields. camelCase both sides (`clearExpires` ↔ `clear_expires`). `write_fields`/`apply_patch_fields` only touch `BackgroundColor` (the `color` tag) — the KDBX `ForegroundColor` attribute is preserved by field edits and managed separately via `update_entry_flags`, so entries created in another KeePass client keep their foreground color unless the user changes it.

`EntryInput` (`add_entry`/`update_entry` payload) = full-field rewrite via a `VaultState` snapshot; icon is a tri-state: `icon` a number → set that built-in index; `icon: null` → reset to the KeePass default icon; `icon` omitted → **keep the entry's current icon** so custom favicon icons survive content-only edits. `tags` is a tri-state string like `color`: present string → parse comma-separated tags (trimmed, empties dropped); empty string → clear all tags; `tags` omitted → **keep the entry's current tags** so non-tag edits never disturb them. (The editor tracks an `iconTouched` flag: untouched icons are never sent, and custom-favicon entries show the web icon as the first option in the icon picker.)

Tags on `VaultEntry` are exposed as a single comma-separated string (`tags: string | null`, matching KeePass's `Entry.tags` storage in the `keepass` crate); the entry-list search in `+page.svelte` matches `[title, username, url, notes, tags]`.

The root group is the virtual top-level (uuid `"root"`); it is not persisted as a KeePass group — its `children` map to top-level groups and its `entries` map to the DB root group entries.

Every mutating command keeps the frontend `vault` store in sync with the backend session. Entry/group CRUD and db-meta mutations return a **light snapshot**: `customIcons` is omitted so favicon image bytes are not re-transmitted on every small edit. Favorite and group-expansion mutations go further and return a `MutationDelta` (revision + affected ids) that the renderer applies to its cached `VaultState` — no tree is rebuilt or serialized for those small changes. `VaultState.customIcons` is authoritative only on open/create/full refresh (`open_vault`/`create_vault`/`get_vault_state`/save paths, including an explicit empty map); `src/lib/services/vault.ts` keeps a module-level icon cache, replaces it whenever an authoritative snapshot arrives, and merges it back into every light mutation result. `favorite` is always present on `VaultEntry` and is persisted as a custom field `SecPivot.Favorite = "true"` (absent when not pinned); the browser fallback mirrors the same boolean on the demo state. `totp_code` computes the entry's one-time password from its OTP seed field (see the OTP field contract below) via the pure primitives in `src-tauri/src/crypto/otp.rs` (RFC 6238 TOTP, RFC 4226 HOTP, Steam Guard). The frontend `TotpWidget`/`EntryTotpBadge` count down locally and refetch at each period boundary; HOTP kinds fetch once and show a static code (their counter only advances when a code is requested).

**Auto-Type contract:** `VaultEntry.autoType?` mirrors KDBX `Entry/AutoType` (`enabled`, `defaultSequence?`, `associations: { window, sequence }[]`) and `VaultGroup.autoType?` mirrors the group flags (`enabled?`, `defaultSequence?`); both are absent when the object stores nothing (group absent = inherit). `update_entry_autotype` replaces the entry config wholesale; `update_group_autotype` replaces the enabled choice (true/false sets, absent/null restores inheritance); its `defaultSequence` is partial (absent keeps, empty clears). The entry editor's 自动填充 tab supplies this config to the required-session `save_entry` transaction together with content, flags, attachments and any website-rule patch. The one result supplies the exact saved UUID and masked state; selection applies only to the captured visible epoch. Standalone `update_entry_autotype` remains available to other callers. The group context menu's 自动填充设置 dialog writes via `update_group_autotype` with an inherit/enable/disable choice plus default sequence. Resolution order for a global-hotkey run is: entry `enabled=false` or an ancestor group `enable_autotype=false` disables the entry entirely; otherwise the first association whose `window` matches the focused window title (case-insensitive, `*` glob) wins, then the entry default sequence, then the nearest ancestor group default. `resolve_autotype_sequence_for_window` exposes this server-side. When the global hotkey matches several entries, the backend emits `autotype-pick-request` with `AutotypeCandidate[]` (`{ sessionId, uuid, title, username }`, best first, recycle bin excluded, capped at 8), remembers the focused window title in that session, and the renderer calls `autotype_pick` with both the originating session id and chosen uuid. Passwords/sequences never leave the backend except through the `auto_type`/`autotype_pick` replay commands.

**OTP field contract** (`src-tauri/src/crypto/otp.rs`, resolved in priority order by `VaultSession::totp_code`): `otp`/`TimeOtp` = TOTP seed (an `otpauth://totp/...` URI honoring `secret`/`algorithm`/`digits`/`period`, or a bare Base32 key defaulting to SHA-1 / 6 digits / 30 s — KeePassXC/KeeWeb compatible); `HmacOtp` = HOTP seed `<Base32>[:<digits>][:<counter>]` (6/0 defaults), whose counter advances on each code request and is written back to the same field (no history snapshot — showing a code never pollutes history, but it does leave the vault dirty so the next save persists the new counter; the entry's `last_modification` is stamped like any other edit so timestamp-based remote merge keeps ordering the counter forward); `SteamOtp`/`steam` = Steam Guard seed (bare Base32; SHA-1 TOTP over 30 s truncated to a 5-character Steam alphabet). A declared `digits` of 0 or above 9 is rejected when computing a code (`compute` returns an error instead of emitting a wrong or empty string — the 31-bit RFC 4226 §5.3 truncation cannot reach a 10-digit modulus). These OTP field names are not part of `RESERVED_FIELDS`, so they round-trip as ordinary custom fields and can be entered from the editor's custom-fields tab. The `otp` field stays reserved and is what the editor's dedicated seed input reads/writes.

`auto_type` follows the KeePass sequence syntax (implemented in `src-tauri/src/platform/autotype.rs`): placeholders `{USERNAME}` `{PASSWORD}` `{TITLE}` `{URL}` `{NOTES}`, special keys `{TAB}` `{ENTER}` `{SPACE}` `{BACKSPACE}` `{DELETE}` `{ESC}` `{UP}` `{DOWN}` `{LEFT}` `{RIGHT}` `{HOME}` `{END}` `{PAGEUP}` `{PAGEDOWN}`, `{{`/`}}` escapes, and literal text. Parsing is pure and unit-tested; keystrokes are replayed via `enigo` 0.6 (`Keyboard::text`/`key`) after a 300 ms grace period on a spawned thread, so the frontend gets the error only if parsing fails — execution failures are logged. The browser fallback rejects `autoType` with a dedicated message.

Global auto-type hotkey (`general.globalAutoTypeShortcut`): `src-tauri/src/lib.rs` registers the accelerator via `tauri-plugin-global-shortcut` at startup and re-registers on every `set_config`. On press, `src-tauri/src/platform/focus.rs` reads the foreground window title (Win32 `GetForegroundWindow`/`GetWindowTextW`, Windows-only, returns `None` elsewhere) and `VaultSession::autotype_match` picks the best entry: URL host contained in the window title scores 2, entry title contained scores 1; the recycle bin subtree is skipped. `VaultSession::resolve_autotype_sequence` then resolves the sequence in KeePass order: the entry's `AutoType.default_sequence`, else the nearest ancestor group's `default_autotype_sequence` (walking up), else the fixed default `{USERNAME}{TAB}{PASSWORD}{ENTER}`. `AutoType.enabled=false` on the entry or `enable_autotype=false` on an ancestor group disables auto-type for that entry (skipped silently). Candidate matching, pending-picker state and replay context are prepared under a short vault lock; Tauri event emission, main-window show/focus operations and keyboard replay happen only after the lock is released. The winner is replayed on a background thread. No match (or locked vault) logs and returns silently.

Field references: `VaultSession::expand_autotype_sequence` resolves `{REF:<Field>@<SearchIn>:<Text>}` (case-insensitive names, substring matching, `I` tolerates missing dashes, `O` matches custom string names) against the whole database except the recycle bin before parsing; unresolved refs abort with `字段引用未找到匹配条目`. `<Field>` accepts the standard codes (`T`/`U`/`P`/`A`/`N`/`I`) **or any non-empty custom string field name** (KeePass `{REF:PIN@T:Bank}` style, matched case-insensitively against the matched entry's custom fields; a bare `O` target stays invalid to avoid ambiguity). Used by the `auto_type` command; the pure parser lives in `autotype.rs::expand_refs` (unit-tested) with the per-entry resolution in `vault.rs`.

TCATO overlay (two-channel auto-type, Windows-oriented): `open_tcato_overlay(uuid)` creates an always-on-top 360×190 window (label `tcato`) that loads the same SPA with a `#/tcato` hash — `src/routes/+page.svelte` renders `TcatoOverlay.svelte` in that mode. The overlay window is set `WS_EX_NOACTIVATE` so clicking its buttons does not steal focus; reopening an existing overlay only re-shows it (no `set_focus`) so the target application keeps keyboard focus; `focus::send_text_to_foreground` injects via `WM_CHAR` (not visible to keyboard hooks, skipping the overlay itself to the next visible window if it is foreground) and rejects empty channels. A second global hotkey (`keyboard.tcatoSummonGlobal`, empty disables) summons the overlay for the entry uniquely matching the foreground window; zero matches summon nothing, several matches open the overlay in pick mode (candidate list, chosen entry re-enters through `open_tcato_overlay`). Each successful inject records the foreground window title per entry (in-memory, cleared on lock) and `tcato_state()` reports it as `lastWindow`. The overlay offers three inject channels — username, password, and the current TOTP code (`tcato_send`); the TOTP channel resolves the live code server-side (HOTP counters advance with detail-widget semantics and mark the vault dirty). The overlay holds only the entry UUID + sessionId (`TcatoTarget` state) and `tcato_state()` exposes `title` + `username` + `hasPassword`/`hasUsername`/`hasTotp` (never the password); recycle-bin entries are rejected (`回收站中的条目不可填充`). `tcato_send(channel)` reads the field from the vault session and injects it; non-Windows falls back to simulated typing. `close_tcato_overlay()` and window `CloseRequested` clear the target and emit `tcato-overlay-close`; vault `close`/`close_all` and tab switch (`set_active_session` when the target session differs, plus frontend `activeId` subscription) also close the overlay and re-arm the focus-loss lock. No real-window runtime evidence exists in this environment; the channel resolution is code-reviewed only.

Keyfile support (`open_vault`/`create_vault` `keyfile` arg): the user picks the keyfile path via the dialog; the backend reads the file bytes, builds the composite `DatabaseKey` (`with_keyfile`), and keeps the raw bytes in the session for re-save, clearing them on `close_vault`. Keyfile formats (XML `<Key><Data>`, 32/64-byte binary, hex) are parsed by the `keepass` crate at key-element time. A passwordless vault is allowed only when a keyfile is present. The browser fallback ignores keyfiles (demo data only).

### Remote vaults (S3 / WebDAV)

`src-tauri/src/remote/` (mod + s3 + webdav + memory + local + backup + tests) defines the `RemoteStorage` trait (`list`/`get`/`put`) with three implementations: `S3Storage` (self-implemented AWS SigV4 over the shared blocking reqwest/rustls client, path-style URLs for custom endpoints such as MinIO; no rust-s3 dependency), `WebDavStorage` (reqwest blocking + PROPFIND multistatus parsing via quick-xml; Basic auth from `accessKey`/`secretKey`, skipped when the username is empty), and `MemoryStorage` (Arc<RwLock<HashMap>>) used by offline tests. `make_storage(cfg)` dispatches on `cfg.kind` (`"s3"`/`"webdav"`); the vault session retains `Arc<dyn RemoteStorage>` with the transport's resolved secondary credentials for subsequent saves until close/reopen. A remote session also holds `RemoteMode` (`InMemory` = upload back only; `SaveLocal` = also mirror locally) and `backup_count`. The display path is `s3://<key>` (kept for both transports); remote paths are excluded from recent files and the lock-screen reopen flow (they need the remote browser, not a local open).

- **S3 endpoint must be an absolute http(s) URL**: `S3Storage::new` rejects scheme-less or non-http(s) endpoints at construction with a clear settings-time message (`S3 服务地址无效`). SigV4 signs the `host` header from the endpoint and every request is sent path-style to `{endpoint}/{bucket}/{key}`, so a bare host (`localhost:9000`) or an opaque `scheme:rest` string would otherwise panic in `host_header` (now a `Result` that errors instead of panicking) or fail with a cryptic reqwest error.
- **WebDAV listing robustness** (compat with real cloud-drive gateways, e.g. 123pan/Nextcloud): `list()` PROPFINDs the collection with a **trailing slash** (`Depth: 1`) — several servers otherwise return only the collection itself, giving an empty list. `parse_multistatus` matches element names case-insensitively and classifies a `<response>` as a file by absence of the collection `resourcetype` (and trailing `/`), **not** by the presence of `getcontentlength` — many gateways omit it (returning a 404 propstat), and requiring it silently dropped every file. A 200 body that is not a multistatus surfaces an actionable error ("不是有效的 multistatus") instead of an empty list.

- **Local mirror layout**: `local_storage_dir(app, profile_path)` → `<data_dir>/Storage/remote/<kind>/<sanitized name>` (data root from `ConfigStore`: portable = beside the executable, installed = app-data dir). The canonical path already separates S3 and WebDAV namespaces; the name segment keeps letters/digits (Unicode-aware) plus `-`/`_`, with other characters normalized to `_`. Saving writes `{name}.kdbx`, rotates the previous file to `{stem}.{timestamp}.{ext}.bak` (chrono `%Y%m%d%H%M%S%.3f`), and prunes to `backupCount` (0 disables). Backups whose generated stamp collides with an existing file (two saves in the same millisecond) get a `_1`/`_2`/… suffix so a rename never silently overwrites a previous backup; the `_N` suffix sorts after the plain stamp so lexicographic pruning still keeps the chronologically newest.
- **Credential resolution and transport lifetime**: list/open/create build a transport from the settings resolved by canonical profile path in `ConfigStore`; the frontend sends only that non-secret path. An open remote session retains its transport for save/refresh/merge jobs, so changing a profile does not automatically replace credentials in that already-open transport. Close/reopen resolves the profile again. These secondary credentials are distinct from the vault master key.
- **Conflict guard**: opening/creating a remote vault records the SHA-256 of the downloaded (or just-uploaded) bytes as the session's sync base hash (`RemoteTarget.base_hash`). Every remote write (`save`, master-key change, storage re-encrypt) re-reads the remote object first and refuses to overwrite when the hash differs, returning `REMOTE_CHANGED`-prefixed errors with remote/local byte sizes; a successful write advances the base hash. Conflicts are not counted as save failures (read-only degradation only applies to genuine persistence errors).
- **`save()` on a remote session** serializes the DB, `put`s it back to the storage, and — in `SaveLocal` mode — additionally writes the local mirror + rotates backups.
- **Bounded timeouts and S3 pagination**: the shared blocking reqwest client uses a 15 s connect timeout. S3 listing follows `IsTruncated` / `NextContinuationToken` within one 30 s deadline; get/put use 120 s request timeouts. The continuation token is an opaque XML-decoded string, encoded once for the signed query. Keys preserve spaces, Unicode, entities and CDATA. Missing/cyclic tokens, invalid XML and failed later pages return errors rather than partial lists. Listing is capped at 100 pages, 10,000 objects, 8 MiB per response and 64 MiB total; users can narrow the prefix on overflow. WebDAV uses 30 s / 120 s per-request timeouts. Failures surface as `S3 列表请求超时…` / `WebDAV 列表请求失败…` (etc.) instead of a UI stuck on "正在加载…".
- **Blocking off the async workers**: the transports block (S3 `block_on`s its own runtime; reqwest blocking `wait::enter`s), which panics on tokio worker threads — the command future aborts and the invoke never resolves (UI stuck on "正在加载…", refresh disabled, no error). Async commands therefore hop to the blocking pool first: `s3_list_objects` delegates to `remote::list_objects_async`; local and remote open/create wrap `prepare_local_open`/`prepare_local_create`/`prepare_remote_open`/`prepare_remote_create`; save, save-as, master-key change, refresh and merge use `prepare_*` → `spawn_blocking(persist_*)` → stable-session `complete_*`. The reqwest blocking client is process-wide (`shared_blocking_client`, built on a dedicated init thread) because the client owns a tokio runtime that must never be built or dropped from an async context. **If such a panic unwinds through a held `MutexGuard<VaultSession>`, the session mutex is poisoned and every later command fails with "数据库锁已损坏"** — never perform remote transport/KDF work under the session lock.
- The transports are covered by offline `MemoryStorage` tests (open/save round-trip, mirror + rotation, invalid key/mode, create→save→reopen, close) **plus** HTTP-level round trips against local mock servers (`s3_transport_round_trips_against_local_mock` — path-style signing, ListObjectsV2 XML parsing, get/put; `webdav_transport_round_trips_against_local_mock` — PROPFIND multistatus parse, collection/self filtering, get/put), bounded-timeout tests, and factory/parser unit tests. S3 additionally has live end-to-end evidence: `remote::tests::s3_transport_round_trips_against_live_s3_server` runs bucket create → put → list → get → delete object → delete bucket against a real local S3-compatible server (MinIO at `B:\Program\s3\minio`, `http://127.0.0.1:9000`, `rustfsadmin`/`rustfsadmin`, path-style) and skips itself when the server is down; the original rustfs local server cannot reach storage readiness on Windows (see `docs/PITFALLS.md`). WebDAV real-provider behavior (e.g. 123pan/Nextcloud) is still code-reviewed only.

### Browser bridge (KeePassHttp)

Split across `src-tauri/src/bridge/{types,crypto,dispatch}.rs` for the pure protocol (request/response types, per-field AES-256-CBC+PKCS7 encryption, verifier, response HMAC, request dispatch) and `src-tauri/src/bridge/server.rs` for the loopback HTTP server, lifecycle (`BridgeState` managed state, started/stopped by `sync_bridge` on startup and every `set_config`), and the associate approval board (`ApprovalBoard` + `bridge_approve` command). The `BridgeHost` trait (implemented by `VaultSession`) isolates session access so the protocol layer is unit-testable without sockets.

- **Transport**: one JSON POST per TCP connection to `127.0.0.1:19455`; headers capped at 16 KiB, body at 1 MiB, read timeout 10 s. The server holds no secrets — a locked vault answers with `{"Success":false,...}` and no auto-unlock.
- **Associate flow**: browser sends `associate`; the loopback server first caps unauthenticated association floods with a 60 s sliding-window limiter (`AssociateRateLimiter` in `server.rs`, max 5 per window) so any local process/page cannot repeatedly surface the approval prompt — excess requests get an immediate failure envelope without emitting the approval event. Under the vault mutex the server then rejects a locked vault, malformed 256-bit key, or bad verifier, and captures the stable backend-active `sessionId`. It then registers a one-shot approval token, emits the Tauri event `bridge-associate-request` (payload `AssociateRequest { token, id }`, never key material) to the frontend `BridgeApprovalPrompt` (mounted in `+layout.svelte`), and waits up to 120 s for `bridge_approve` **outside** the vault mutex. The token is removed after allow, deny, or timeout, so a late response cannot revive an expired request. After approval the server reacquires the mutex and registers the key only if the captured session is still backend-active; a tab switch/close rejects the request instead of binding it to another vault. The pending AES key stays in a zeroizing backend-only object throughout the wait. On approval the client gets `{ Id, Key, Hash, Verifier, Success }`; keys are held in the session (`bridge_keys`) and wiped by `close_vault`. Re-associate with a known id refreshes that client's key.
- **Matching and writes**: `get-logins` uses `url_host` host-equal-or-subdomain matching against entry URLs (same rule family as auto-type; the recycle bin subtree is skipped); entries carry `Uuid` (hex), `Login`/`Password`/`Url`/`SubmitUrl` encrypted, `Name`, `Realm` (empty), and `Totp?` when present. `set-login` updates only a referenced entry's changed username/password (the submitted page URL is not allowed to overwrite its canonical URL), creates a KeePass history snapshot for a real change, or creates a new entry titled by the URL host. A real mutation marks the session dirty, and every successful request emits `browser-vault-changed` so the desktop publishes the entry and dirty tab immediately. This mirrors KeePassHttp's `CreateBackup` + `UpdateUI` behavior; it deliberately does not force a database save, so the normal visible save/lock workflow remains authoritative. `get-logins-count` counts matches without payloads. `generate-password` returns a fresh 20-char password (upper/lower/digits/symbols, one per category — mirrors the app's `DEFAULT_DATABASE_SETTINGS.generator`) in the plaintext `Password` response field: it is newly generated for the browser to fill a form, not a vault secret, so it is not field-encrypted (still HMAC-authenticated via the response envelope).
- **`db_hash`**: SHA1 of (root group uuid ‖ recycle-bin group uuid) rendered as 40 lowercase hex chars — it changes whenever the vault structure changes, so browsers re-ask on identity changes.
- **Verifier/HMAC**: per KeePassHttp, the request `Verifier` = AES-256-CBC(key, iv = request nonce bytes) encrypting the base64 string of those nonce bytes — the server decrypts it and compares against `base64(nonce)`. Every response carries a fresh random `Nonce` (used as the AES-CBC IV for its encrypted fields) and `Hmac` = HMAC-SHA256(key, response `Nonce` bytes ‖ response `Verifier` ciphertext bytes); a fresh `Verifier` is likewise derived under the new nonce. Both sides validate accordingly. Tests cover NIST SP 800-38A block 1, RFC 4231 case 2, tamper rejection, and encrypted round-trips (offline; no real-browser E2E evidence in this environment).

Outside Tauri, `services/vault.ts` simulates the same commands on `demo-vault.ts` data persisted to `localStorage`. An open demo uses the synthetic `browser` session id, assigned before publishing the first snapshot (refresh/open/create); close and lock clear it before publishing null. The internal getter and tab stores thus agree and template/view guards can execute normally. It is a UI-development surface only and must never be used as evidence for desktop KDBX behavior.

### KeePassRPC bridge (Kee 4.x)

Split across `src-tauri/src/rpc/{mod,dto,srp,keys,dispatch}.rs` (pure protocol: SRP-6a math, key-auth challenge/response, AES-256-CBC + SHA-1 MAC frame crypto, v1 JSON-RPC method dispatch) and `src-tauri/src/rpc/server/{mod,handshake,tests}.rs` (loopback WebSocket server on `127.0.0.1:12546`, `RpcState` lifecycle started/stopped by `sync_rpc` on startup and every `set_config`, per-connection handshake state machine). The `RpcHost` trait (implemented by `VaultSession`, keys in `rpc_keys`, wiped on tab close and conditionally retained across the all-tabs lock as described above) isolates session access so the protocol layer is unit-testable without sockets.

- **Transport**: WebSocket upgrade required; valid handshakes to paths other than `/` and plain HTTP availability probes get 404 with CORS. Upgrade detection preserves fresh bounded peek snapshots, waits for the real header terminator and limits only the head to 64 KiB within a 30 s observation deadline. The initial logical read timeout is 30 s; after WebSocket upgrade it becomes 300 s per read, including setup messages. This is not a total SRP setup deadline. Payload cap 1 MiB.
- **SRP-6a setup**: client sends `{protocol:"setup", srp:{stage:"identifyToServer", I, A}}`; the server generates a one-time side-channel password (8 random bytes as 16 lowercase hex chars, 120 s TTL), emits the Tauri event `rpc-side-channel-request` (payload `SideChannelRequest { requestId, password, expiresInSecs }` — shown in the desktop UI only via `RpcSideChannelPrompt` in `+layout.svelte`, never logged or persisted) and replies `identifyToClient {s, B, securityLevel}` with `features`. The proof exchange (`proofToServer` M / `proofToClient` M2) follows SRP-6a (1024-bit group); on success the derived session key (K = H(S)) is registered under the client username via `register_rpc_key` and mirrored per-connection. Error envelope codes: `AUTH_FAILED` (wrong password or vault locked), `AUTH_EXPIRED` (side-channel password expired).
- **Stored-key setup** (`key:{username}` → `key:{sc}` → `key:{cc,cr}` → `key:{sr}`): both challenge and proof require the same current host key under the captured username; revoked, expired or rotated challenges answer `AUTH_RESTART`. `rpc.keepSessionAfterLock` retains backend-active keys across the all-tabs lock, so stored-key authentication can still succeed while locked; data requests remain locked. Ordinary tab close always wipes its keys. `cr`/`sr` = SHA-256 over `"1"|secret|sc|cc` / `"0"|secret|sc|cc`.
- **JSON-RPC frames**: `{protocol:"jsonrpc", jsonrpc:{message,iv,hmac}}` with AES-256-CBC (fresh IV) and the protocol's naive MAC `base64(SHA-1(SHA-1(key)||ct||iv))`. Read-only methods (GetAllDatabases, FindLogins, GetPasswordProfiles, GeneratePassword) dispatch under a short `VaultSession` lock. `AddLogin`/`UpdateLogin` instead decode and validate once, capture the backend-active `sessionId`, then run prepare → KDF/serialization/storage persist → complete; only prepare/complete hold the session/registry locks, and all blocking persistence runs outside them. Responses are JSON-RPC 2.0 with numeric `id` echo. Tampered frames or a key wiped by lock close the connection without a reply.
- **Write path** (`AddLogin`/`UpdateLogin`, mirroring KeePassRPC `KeePassRPCService.JSONRPC.cs` + `MergeEntries`/`MergeInNewURLs`): `AddLogin [EntryDTO, parentUUID, dbFileName]` creates an entry (uuid server-generated) under the parent group (empty/unresolvable → root; a parent inside the recycle bin is skipped); `UpdateLogin [EntryDTO, oldLoginUUID, urlMergeMode, dbFileName]` requires non-empty `oldLoginUUID`/`dbFileName` and updates in place with a history snapshot (the plugin's `CreateBackup`), rejecting entries in the recycle bin. Field mapping follows `setPwEntryFromEntry`: first `FFTpassword` → `Password`, all `FFTusername` → `UserName` (last wins), remaining fields → custom strings named `displayName` (fallback `name`); `uRLs[0]` → `URL`, extra URLs space-joined into the same field so the read path sees every URL. URL merging (`merge_urls`) implements all five `urlMergeMode` modes (1 merge-new-first, 2 delete-old-primary-then-merge, 3 keep-old-append-new, 4 unchanged, 5 whole-list replace; unknown → 4); the server offers `KPRPC_FEATURE_ENTRY_URL_REPLACEMENT` so Kee sends mode 5. The prepare phase mutates only a cloned database and pre-generates a stable UUID for adds; a persist failure therefore leaves the live session unchanged. A process-local persistence gate serializes every runtime transaction that writes a vault or local mirror (create, remote open/refresh mirroring, save/re-encrypt/change-key/save-as, remote merge, favicon auto-save and RPC) from prepare through completion without holding the session lock, preventing two successful stale snapshots from overwriting each other on disk. Completion is bound to the captured originating session even after a tab switch. If other in-memory edits arrived meanwhile, the RPC operation is replayed onto the current database and the session stays dirty so both changes reach the next save; for a concurrent edit of the same entry, the later RPC fields win and the UI intermediate state remains in KeePass history. If the originating tab closes or a concurrent delete makes replay impossible after persistence, the protocol still returns the DTO captured from the successfully persisted snapshot rather than reporting a false failure. Responses are the updated entry DTO with an embedded `db` summary. Errors: `-32001` "oldLoginUUID could not be resolved to an existing entry.", `-32002` "Entry is in the Recycle Bin.", `-32600` for the plugin's `ArgumentException` mirrors. (Deviation: extra fields are stored as KDBX strings rather than the plugin's private "KPRPC JSON" config; the update path overwrites fields but does not delete stale custom fields.)
- **Authorization admission**: the socket's cached key is revalidated against the current host before read dispatch and, after the persistence gate, before `AddLogin`/`UpdateLogin` preparation. Missing/expired/rotated keys close the data path. A pending SRP proof additionally requires the original stable `VaultSessions` id and an open host, so it cannot authorize a new tab or a lock/reopen session. An already admitted storage write still completes and adopts its durable result even if authorization expires afterward.
- **Locked vault**: new SRP and late SRP proofs are refused (`AUTH_FAILED`). Absent stored keys require `AUTH_RESTART`; configured retained keys may authenticate, but JSON-RPC data requests answer `Vault is locked`. The bridge never serves vault data while locked and never auto-unlocks.
- Offline verification only: protocol state machines are tested with the extension's own `SRPc` math (JS-mirror client) and raw-socket WS handshake/framing smoke tests; no real Kee 4.x E2E evidence exists in this environment.

## Serialization rules

- KDBX entry/group uuids are rendered as hex strings; group UUIDs are stable for the session.
- `password` never enters `VaultState` or the Tauri `VaultEntry` payload; reveal, copy, edit-prefill, CSV export, and the security report resolve entry passwords server-side (`get_entry_password`, `export_csv`, `security_report`). The browser fallback keeps demo passwords in `VaultEntry.password` for its local simulation. Entry passwords never enter config, logs, or error strings.
- Protected custom fields follow the same rule as passwords: their `value` is always empty in the Tauri `VaultEntry` snapshot (only the `protected` flag travels), and reveal/copy/editor-prefill resolve the value server-side via `get_custom_field_value`. The editor fetches protected values on demand before saving and gates the save button until they settle, so saving an edit never overwrites a protected value with an empty string. CSV export and the history payload keep protected values server-side (export is explicit user action; history restore is index-based and never displays the value in the UI).
- `modifiedAt` is refreshed and `revision` incremented on every mutation; mutation snapshots expose the new revision so the renderer can order/merge results and detect stale responses.

manual suffix subset. Private hosted tenants (github.io/blogspot.com/etc.),
wildcards and exceptions retain their true registrable boundaries. IP literals
and hosts with no registrable domain compare using their full host identities.
Only Domain accuracy with matchByRegistrableDomain enabled uses this lookup;
default/explicit Hostname/Exact rules and existing blocked/regex lists are unchanged.
The list is built into the binary: credential matching performs no network reads.
Review snapshot dependency updates with tenant, wildcard, exception and IP tests.

`util::url_host(&str) -> Option<String>` extracts the actual destination through
the existing url crate: userinfo is excluded, domains use canonical ASCII IDNA,
and IP literals use normalized addresses (IPv6 without brackets). Bare host:port
and protocol-relative URLs remain valid. Invalid authorities, internal whitespace
and ambiguous bare userinfo return None; there is no new DTO/IPC/dependency.
`util::url_authority` supplies that host plus an optional explicit numeric port.
Hostname (`blockDomainOnlyMatch`) compares both, including explicitly written
default ports; an omitted port stays None and no scheme default is invented.
Domain deliberately retains its looser host/site scope across different ports.
`match-url.ts` uses WHATWG URL validation and retains the same explicit port for
Hostname suggestions, canonical ASCII IDNA and bracketed IPv6 for URL rules.
The shared strict-JSON corpus under `tests/fixtures/url-authorities.json` covers
both parsers and actual suggested alt rules after synthetic KDBX reopen.
No public DTO/IPC/config/dependency changes are involved.

KPRPC `blockHostnameOnlyMatch` selects Exact: after host validation, the complete
URL strings must be identical, including scheme/path case/query/fragment/port.
Bridge preserves request and submit-URL case before calling the shared matcher;
only destination-host extraction performs case normalization.
Explicit regex allow and blocked lists retain their existing priority. The
renderer `match-url.ts::shortestMatchable` returns the original trimmed URL for
Exact suggestions; it never removes query/fragment or invents a scheme. There is
no new setting or IPC. Tests cover both host adapters after KDBX reopen and the
frontend suggestion value; native extension interoperability remains unverified.

`DatabaseSettingsPatch` uses `dto::de_nullable_patch` for historyMaxItems,
historyMaxSize, recycleBinEnabled and entryTemplatesGroup. Wire absence means
keep, explicit JSON null means reset, and a typed value means set. The generic
deserializer preserves outer Some for present null without accepting wrong
value types. Metadata-only and re-encryption paths consume the same DTO; normal
kdf/cipher/compression option semantics and the icon deserializer are unchanged.
Native wire/save/reopen regressions cover the boundary; constructing Some(None)
in Rust alone is not proof of the JSON IPC reset contract.
