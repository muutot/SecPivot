# Data Contracts

This reference defines the frontend ↔ backend contract. Update it together with any change to IPC commands, serde types, config schema, or vault serialization.

- `get_config() -> AppConfig`: read + normalize; returns defaults on first run.
- `set_config(config: AppConfig) -> AppConfig`: normalize + atomic save; returns the normalized value.

Frontend normalization lives in `services/settings.ts::normalizeSettings`; the backend must apply the same range/default rules so the round-trip is idempotent. New settings fields require both sides plus tests.

> **Pitfall — serde silently drops unknown fields.** The Rust `AppConfig` structs have no `deny_unknown_fields`, so a frontend field missing from the Rust serde shape is quietly discarded on `set_config`, written to disk, and returned as absent — the UI keeps it in memory via the fallback, but it **resets on the next launch**. Symptom: "my settings don't stick after restart", especially per-sub-item values while a parent toggle (e.g. `compactMode`) persists. Every new settings field must be mirrored in: TypeScript type + defaults + `normalizeSettings` (frontend), Rust serde struct + `Default` + `normalize_config` clamp (backend), and this table. The regression test `density_survives_deserialize_write_reload` guards the round-trip.

> **Pitfall — the read side: missing fields must not crash load.** Deserialization is strict by default: a required field absent from an existing `config.json` (old version, manual edit) makes `ConfigStore::load` fail, which propagates from the setup hook and **panics the app on startup**. Settings structs therefore use container-level `#[serde(default)]` (every struct also impls `Default`), while `AppConfig` applies `#[serde(default)]` per field. When adding a field, keep the matching `Default` impl current and add a load test. Guarded by `old_config_without_density_loads_with_defaults` and `empty_config_object_loads_with_defaults`.

## Vault IPC contract

The vault session is held in backend managed state and returned to the frontend as serialized `VaultState`.

### Shared types (Rust serde ↔ `src/lib/types/vault.ts`)

| Type         | Fields                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VaultEntry` | `uuid`, `groupUuid`, `title`, `username`, `password?` (browser demo only, never in the Tauri runtime), `url`, `notes`, `totp?`, `icon?`, `created?`, `modified?`, `tags?`, `overrideUrl?` (KeePass `OverrideURL`, matching-only), `foregroundColor?` (`#RRGGBB` KeePass `ForegroundColor`), `favorite: bool`, `qualityCheck: bool`, `customData: CustomDataEntry[]`, `customFields: CustomField[]`, `attachments: AttachmentInfo[]` |

KeePass's `OverrideURL` field is honored for matching only: `helpers::entry_primary_url` returns `OverrideURL` when set (non-empty) and falls back to `URL`; it feeds `entry_match_urls` (bridge/RPC/auto-type URL lists and title scoring) and the host-tier match in `kprpc_matches_url`. The DTO `url` field, the `{URL}` auto-type placeholder, CSV export, and all write paths still use the literal `URL` field — OverrideURL is a read-side matching override, never surfaced as the display URL. It is editable via `update_entry_flags` (empty string clears it, trimmed on write); `VaultEntry.overrideUrl` exposes the current value for the editor, and `VaultEntry.qualityCheck`/`foregroundColor` are likewise writable through `update_entry_flags`.

KeePass per-entry `QualityCheck` is exposed as `qualityCheck` (KDBX default `true`) and is writable through `update_entry_flags`; ordinary field edits preserve it. An entry with `qualityCheck == false` is excluded from the security report's `empty` and `weak` findings (KeePass opts the entry out of password-quality evaluation) while still counting toward `total` and still participating in `duplicates` (password reuse is a separate concern). Entries created by SecPivot keep the crate default of `true` unless the editor explicitly changes it.

KDBX `CustomData` maps at all three levels (entry, group, database-meta) are projected read-only into `CustomDataEntry[]` (`{ key, value?, binary?, modified? }`, sorted by key; string values are plaintext, binary values base64) on `VaultEntry.customData`, `VaultGroup.customData`, and `VaultState.metaCustomData`. SecPivot never writes these — they are plugin metadata authored by other KeePass clients and must survive edits and saves untouched; `write_fields`/`apply_patch_fields`/`sync_custom_fields` and group mutations never touch `custom_data`. Fidelity is verified by the `custom_data_round_trips_through_edit_and_save` test and the cross-client `foreign_attributes_survive_edits_and_flags_round_trip` test, which seeds entry/group CustomData plus foreign OverrideURL/colors/quality/group meta, runs SecPivot field + flag + group-meta edits, and asserts everything survives save + reopen (no real second KeePass client runs in CI).

The database meta name and description (`DatabaseName`/`DatabaseDescription`) are exposed on `VaultState.databaseName?`/`databaseDescription?` (KDBX `None` reads as absent) and are editable via `update_db_meta` — each arg is a tri-state: present string (including empty) sets the KDBX meta field, omitted leaves it untouched; an empty string clears the field. Both setters also refresh the corresponding `..._changed` KDBX meta timestamp. Like entry edits, this marks the vault dirty and bumps the revision, so the frontend must refresh `VaultState` afterwards (the command returns it).

`WeakEntry` = `{ uuid, bits }`; `DuplicatePasswords` = `{ count, uuids }`; `SimilarPasswordGroup` = `{ entries: SimilarEntry[] }` where `SimilarEntry` = `{ uuid, title, username }` — similar-password clusters (at most two edits apart), passwords never included.

**Multi-session registry (tabs):** `src-tauri/src/vault/sessions.rs::VaultSessions` (managed state) parks every non-active session under a stable generated `sessionId` (`s1`, `s2`, …); the backend-active session always lives in the app's `Mutex<VaultSession>`. Opening/creating a vault parks the previous active session under its existing id and activates the new one, so several databases stay decrypted in memory at once. Every renderer-originated session command captures and sends `sessionId`; command wrappers route through `VaultSessions::with_session_mut` instead of assuming the backend-active slot (omission remains a compatibility fallback only). The frontend keeps a `VaultState`/custom-icon cache per session, rejects lower-revision late snapshots and every response from before a whole-session replacement (remote download epoch), and publishes results only while that id is still visible. Service methods return that actually committed cache state when a late raw response is rejected, and tab-list refresh retains a renderer active id only while the backend still lists it. Composite operations explicitly reuse their starting id, extracted attachment tokens are owner-bound in the backend store (not merely trusted from the renderer), TOTP cache keys include the session id, and session-scoped dialogs, menus, mobile drawers, selections, loaded secrets, status notices, and sensitive export choices are cleared on a tab change. The group tree is keyed by the session that owns the published `VaultState`, not merely the earlier active-id notification, so identical copied databases cannot reuse expansion, rename, or context-menu component state. Page-level long operations additionally capture a visible-session epoch: returning A after A→B starts a new epoch, so the first A view cannot reopen reports or clear `busy`/form-saving flags belonging to the new A view; latest-operation tokens also prevent older same-view completions from clearing a newer activity. Delayed expiry notices use the same epoch and are deduplicated by `sessionId:path`, preventing a previous tab from flashing after a switch while still allowing the browser demo's fixed `browser` id to open another path. The entry editor awaits the parent's complete create/edit/autotype/flags promise, blocks cancel/re-submit until it settles, and the parent applies close/selection/toast results only to the captured visible epoch. Native file dialogs capture that epoch before opening: import actions discard stale picker/read/parser results before any database write, and save-as discards a stale chosen path before `save_vault_as`; once an import starts, every group-creation iteration and the final batch insert explicitly reuse the original session id. `set_active_session` is idempotent and each complete frontend switch attempt (including an uncached tab's snapshot validation) is synchronously enqueued before any wait; validation failure therefore cannot leave the renderer restored to one tab while a previously queued backend swap later activates another, and rapid A→B→A requests finish in click order. Every renderer topology operation (`open`/`create`, remote open/create, close/close-tab/close-all, and tab switch) shares that same queue, so its backend registry mutation and matching frontend publish finish atomically in invocation order. Bridge/RPC/global-hotkey access remains intentionally limited to the backend-active session. Long prepare/persist/complete commands (`save_vault`, `save_vault_as`, `change_master_key`, `download_favicons`) carry the originating id through every phase; favicon progress and Auto-Type picker events also carry the owner id and are ignored by other tabs. `close_all_vaults` closes every session (the lock path), closing active promotes the last parked session, and the screen-capture guard stays on while any session remains open. Frontend behavior tests cover switch/topology ordering, invalid-active fallback, visible-epoch invalidation, failure and stale-state rejection, while the backend regression duplicates one KDBX so both tabs have identical entry UUIDs and proves an addressed mutation changes only the named session.

`CustomField` (in `VaultEntry`/`HistoryVersion`/`EntryInput`) = `{ name, value, protected: bool }`. In the Tauri runtime a protected field's snapshot `value` is **always empty** — the real value never leaves the session and is resolved on demand via `get_custom_field_value` (reveal, copy, and editor prefill); the `protected` flag itself is always serialized. Writes go through `update_custom_field` (one value at a time, protected flag carried by the caller so an inline edit never downgrades a protected field). Unprotected fields carry their value in the snapshot as before. The browser demo fallback keeps protected values inline for its local simulation only.

`EntryPatch` (batch edit payload) = optional `title`, `username`, `password`, `url`, `notes`, `totp` (empty string clears the seed), `expires` (empty string clears the expiry), `icon`, `color` (empty string clears the tag), `tags` (empty string clears the tags) plus boolean `clearExpires` / `clearIcon` / `clearColor`. An absent field leaves every target entry untouched — passwords are never fetched or re-sent for unchanged fields. camelCase both sides (`clearExpires` ↔ `clear_expires`). `write_fields`/`apply_patch_fields` only touch `BackgroundColor` (the `color` tag) — the KDBX `ForegroundColor` attribute is preserved by field edits and managed separately via `update_entry_flags`, so entries created in another KeePass client keep their foreground color unless the user changes it.

`EntryInput` (`add_entry`/`update_entry` payload) = full-field rewrite via a `VaultState` snapshot; icon is a tri-state: `icon` a number → set that built-in index; `icon: null` → reset to the KeePass default icon; `icon` omitted → **keep the entry's current icon** so custom favicon icons survive content-only edits. `tags` is a tri-state string like `color`: present string → parse comma-separated tags (trimmed, empties dropped); empty string → clear all tags; `tags` omitted → **keep the entry's current tags** so non-tag edits never disturb them. (The editor tracks an `iconTouched` flag: untouched icons are never sent, and custom-favicon entries show the web icon as the first option in the icon picker.)

Tags on `VaultEntry` are exposed as a single comma-separated string (`tags: string | null`, matching KeePass's `Entry.tags` storage in the `keepass` crate); the entry-list search in `+page.svelte` matches `[title, username, url, notes, tags]`.

The root group is the virtual top-level (uuid `"root"`); it is not persisted as a KeePass group — its `children` map to top-level groups and its `entries` map to the DB root group entries.

Every mutating command keeps the frontend `vault` store in sync with the backend session. Entry/group CRUD and db-meta mutations return a **light snapshot**: `customIcons` is omitted so favicon image bytes are not re-transmitted on every small edit. Favorite and group-expansion mutations go further and return a `MutationDelta` (revision + affected ids) that the renderer applies to its cached `VaultState` — no tree is rebuilt or serialized for those small changes. `VaultState.customIcons` is authoritative only on open/create/full refresh (`open_vault`/`create_vault`/`get_vault_state`/save paths, including an explicit empty map); `src/lib/services/vault.ts` keeps a module-level icon cache, replaces it whenever an authoritative snapshot arrives, and merges it back into every light mutation result. `favorite` is always present on `VaultEntry` and is persisted as a custom field `SecPivot.Favorite = "true"` (absent when not pinned); the browser fallback mirrors the same boolean on the demo state. `totp_code` computes the entry's one-time password from its OTP seed field (see the OTP field contract below) via the pure primitives in `src-tauri/src/crypto/otp.rs` (RFC 6238 TOTP, RFC 4226 HOTP, Steam Guard). The frontend `TotpWidget`/`EntryTotpBadge` count down locally and refetch at each period boundary; HOTP kinds fetch once and show a static code (their counter only advances when a code is requested).

**Auto-Type contract:** `VaultEntry.autoType?` mirrors KDBX `Entry/AutoType` (`enabled`, `defaultSequence?`, `associations: { window, sequence }[]`) and `VaultGroup.autoType?` mirrors the group flags (`enabled?`, `defaultSequence?`); both are absent when the object stores nothing (group absent = inherit). `update_entry_autotype` replaces the entry config wholesale; `update_group_autotype` is partial (absent fields keep the current value, empty `defaultSequence` clears it). The entry editor's 自动填充 tab collects the config and the page applies it via `update_entry_autotype` right after the main add/update save (the entry uuid exists only then); the entire fields → Auto-Type → flags chain reuses the starting `sessionId`, and only selects from the final snapshot when that session is still visible. The group context menu's 自动填充设置 dialog writes via `update_group_autotype` with an inherit/enable/disable choice plus default sequence. Resolution order for a global-hotkey run is: entry `enabled=false` or an ancestor group `enable_autotype=false` disables the entry entirely; otherwise the first association whose `window` matches the focused window title (case-insensitive, `*` glob) wins, then the entry default sequence, then the nearest ancestor group default. `resolve_autotype_sequence_for_window` exposes this server-side. When the global hotkey matches several entries, the backend emits `autotype-pick-request` with `AutotypeCandidate[]` (`{ sessionId, uuid, title, username }`, best first, recycle bin excluded, capped at 8), remembers the focused window title in that session, and the renderer calls `autotype_pick` with both the originating session id and chosen uuid. Passwords/sequences never leave the backend except through the `auto_type`/`autotype_pick` replay commands.

**OTP field contract** (`src-tauri/src/crypto/otp.rs`, resolved in priority order by `VaultSession::totp_code`): `otp`/`TimeOtp` = TOTP seed (an `otpauth://totp/...` URI honoring `secret`/`algorithm`/`digits`/`period`, or a bare Base32 key defaulting to SHA-1 / 6 digits / 30 s — KeePassXC/KeeWeb compatible); `HmacOtp` = HOTP seed `<Base32>[:<digits>][:<counter>]` (6/0 defaults), whose counter advances on each code request and is written back to the same field (no history snapshot — showing a code never pollutes history, but it does leave the vault dirty so the next save persists the new counter); `SteamOtp`/`steam` = Steam Guard seed (bare Base32; SHA-1 TOTP over 30 s truncated to a 5-character Steam alphabet). A declared `digits` of 0 or above 9 is rejected when computing a code (`compute` returns an error instead of emitting a wrong or empty string — the 31-bit RFC 4226 §5.3 truncation cannot reach a 10-digit modulus). These OTP field names are not part of `RESERVED_FIELDS`, so they round-trip as ordinary custom fields and can be entered from the editor's custom-fields tab. The `otp` field stays reserved and is what the editor's dedicated seed input reads/writes.

`auto_type` follows the KeePass sequence syntax (implemented in `src-tauri/src/platform/autotype.rs`): placeholders `{USERNAME}` `{PASSWORD}` `{TITLE}` `{URL}` `{NOTES}`, special keys `{TAB}` `{ENTER}` `{SPACE}` `{BACKSPACE}` `{DELETE}` `{ESC}` `{UP}` `{DOWN}` `{LEFT}` `{RIGHT}` `{HOME}` `{END}` `{PAGEUP}` `{PAGEDOWN}`, `{{`/`}}` escapes, and literal text. Parsing is pure and unit-tested; keystrokes are replayed via `enigo` 0.6 (`Keyboard::text`/`key`) after a 300 ms grace period on a spawned thread, so the frontend gets the error only if parsing fails — execution failures are logged. The browser fallback rejects `autoType` with a dedicated message.

Global auto-type hotkey (`general.globalAutoTypeShortcut`): `src-tauri/src/lib.rs` registers the accelerator via `tauri-plugin-global-shortcut` at startup and re-registers on every `set_config`. On press, `src-tauri/src/platform/focus.rs` reads the foreground window title (Win32 `GetForegroundWindow`/`GetWindowTextW`, Windows-only, returns `None` elsewhere) and `VaultSession::autotype_match` picks the best entry: URL host contained in the window title scores 2, entry title contained scores 1; the recycle bin subtree is skipped. `VaultSession::resolve_autotype_sequence` then resolves the sequence in KeePass order: the entry's `AutoType.default_sequence`, else the nearest ancestor group's `default_autotype_sequence` (walking up), else the fixed default `{USERNAME}{TAB}{PASSWORD}{ENTER}`. `AutoType.enabled=false` on the entry or `enable_autotype=false` on an ancestor group disables auto-type for that entry (skipped silently). Candidate matching, pending-picker state and replay context are prepared under a short vault lock; Tauri event emission, main-window show/focus operations and keyboard replay happen only after the lock is released. The winner is replayed on a background thread. No match (or locked vault) logs and returns silently.

Field references: `VaultSession::expand_autotype_sequence` resolves `{REF:<Field>@<SearchIn>:<Text>}` (case-insensitive names, substring matching, `I` tolerates missing dashes, `O` matches custom string names) against the whole database except the recycle bin before parsing; unresolved refs abort with `字段引用未找到匹配条目`. Used by the `auto_type` command; the pure parser lives in `autotype.rs::expand_refs` (unit-tested) with the per-entry resolution in `vault.rs`.

TCATO overlay (two-channel auto-type, Windows-oriented): `open_tcato_overlay(uuid)` creates/focuses an always-on-top 360×190 window (label `tcato`) that loads the same SPA with a `#/tcato` hash — `src/routes/+page.svelte` renders `TcatoOverlay.svelte` in that mode. The overlay holds only the entry UUID (`TcatoTarget` state) and `tcato_state()` exposes title + `hasPassword` (never the password). `tcato_send(channel)` reads the field from the vault session and `focus::send_text_to_foreground` injects it into the foreground window via `WM_CHAR` messages (not visible to keyboard hooks); non-Windows falls back to simulated typing. `close_tcato_overlay()` closes the window. No real-window runtime evidence exists in this environment; the channel resolution is code-reviewed only.

Keyfile support (`open_vault`/`create_vault` `keyfile` arg): the user picks the keyfile path via the dialog; the backend reads the file bytes, builds the composite `DatabaseKey` (`with_keyfile`), and keeps the raw bytes in the session for re-save, clearing them on `close_vault`. Keyfile formats (XML `<Key><Data>`, 32/64-byte binary, hex) are parsed by the `keepass` crate at key-element time. A passwordless vault is allowed only when a keyfile is present. The browser fallback ignores keyfiles (demo data only).

### Remote vaults (S3 / WebDAV)

`src-tauri/src/remote/` (mod + s3 + webdav + memory + local + backup + tests) defines the `RemoteStorage` trait (`list`/`get`/`put`) with three implementations: `S3Storage` (rust-s3 0.34, path-style, custom `Region::Custom` endpoint so MinIO works), `WebDavStorage` (reqwest blocking + PROPFIND multistatus parsing via quick-xml; Basic auth from `accessKey`/`secretKey`, skipped when the username is empty), and `MemoryStorage` (Arc<RwLock<HashMap>>) used by offline tests. `make_storage(cfg)` dispatches on `cfg.kind` (`"s3"`/`"webdav"`); the vault session only ever holds `Arc<dyn RemoteStorage>`. A remote session also holds `RemoteMode` (`InMemory` = upload back only; `SaveLocal` = also mirror locally) and `backup_count`. The display path is `s3://<key>` (kept for both transports); remote paths are excluded from recent files and the lock-screen reopen flow (they need the remote browser, not a local open).

- **S3 endpoint must be an absolute http(s) URL**: `S3Storage::new` rejects scheme-less or non-http(s) endpoints at construction with a clear settings-time message (`S3 服务地址无效`). SigV4 signs the `host` header from the endpoint and every request is sent path-style to `{endpoint}/{bucket}/{key}`, so a bare host (`localhost:9000`) or an opaque `scheme:rest` string would otherwise panic in `host_header` (now a `Result` that errors instead of panicking) or fail with a cryptic reqwest error.
- **WebDAV listing robustness** (compat with real cloud-drive gateways, e.g. 123pan/Nextcloud): `list()` PROPFINDs the collection with a **trailing slash** (`Depth: 1`) — several servers otherwise return only the collection itself, giving an empty list. `parse_multistatus` matches element names case-insensitively and classifies a `<response>` as a file by absence of the collection `resourcetype` (and trailing `/`), **not** by the presence of `getcontentlength` — many gateways omit it (returning a 404 propstat), and requiring it silently dropped every file. A 200 body that is not a multistatus surfaces an actionable error ("不是有效的 multistatus") instead of an empty list.

- **Local mirror layout**: `local_storage_dir(app, profile_path)` → `<app_data>/Storage/remote/<kind>/<sanitized name>`. The canonical path already separates S3 and WebDAV namespaces; the name segment keeps letters/digits (Unicode-aware) plus `-`/`_`, with other characters normalized to `_`. Saving writes `{name}.kdbx`, rotates the previous file to `{stem}.{timestamp}.{ext}.bak` (chrono `%Y%m%d%H%M%S%.3f`), and prunes to `backupCount` (0 disables). Backups whose generated stamp collides with an existing file (two saves in the same millisecond) get a `_1`/`_2`/… suffix so a rename never silently overwrites a previous backup; the `_N` suffix sorts after the plain stamp so lexicographic pruning still keeps the chronologically newest.
- **Credentials travel per command**: each command builds a fresh transport from the settings resolved by canonical profile path in `ConfigStore`; the frontend sends only that non-secret path, and nothing is cached in the session.
- **Conflict guard**: opening/creating a remote vault records the SHA-256 of the downloaded (or just-uploaded) bytes as the session's sync base hash (`RemoteTarget.base_hash`). Every remote write (`save`, master-key change, storage re-encrypt) re-reads the remote object first and refuses to overwrite when the hash differs, returning `REMOTE_CHANGED`-prefixed errors with remote/local byte sizes; a successful write advances the base hash. Conflicts are not counted as save failures (read-only degradation only applies to genuine persistence errors).
- **`save()` on a remote session** serializes the DB, `put`s it back to the storage, and — in `SaveLocal` mode — additionally writes the local mirror + rotates backups.
- **Bounded timeouts**: S3 sets a 15 s connect timeout (`with_request_timeout`) and wraps each call in `tokio::time::timeout` — 30 s for `list`, 120 s for `get`/`put`. WebDAV sets the same timeouts per request on the blocking client. Failures surface as `S3 列表请求超时…` / `WebDAV 列表请求失败…` (etc.) instead of a UI stuck on "正在加载…".
- **Blocking off the async workers**: the transports block (S3 `block_on`s its own runtime; reqwest blocking `wait::enter`s), which panics on tokio worker threads — the command future aborts and the invoke never resolves (UI stuck on "正在加载…", refresh disabled, no error). Async commands therefore hop to the blocking pool first: `s3_list_objects` delegates to `remote::list_objects_async`; local and remote open/create wrap `prepare_local_open`/`prepare_local_create`/`prepare_remote_open`/`prepare_remote_create`; save, save-as, master-key change, refresh and merge use `prepare_*` → `spawn_blocking(persist_*)` → stable-session `complete_*`. The reqwest blocking client is process-wide (`shared_blocking_client`, built on a dedicated init thread) because the client owns a tokio runtime that must never be built or dropped from an async context. **If such a panic unwinds through a held `MutexGuard<VaultSession>`, the session mutex is poisoned and every later command fails with "数据库锁已损坏"** — never perform remote transport/KDF work under the session lock.
- The transports are covered by offline `MemoryStorage` tests (open/save round-trip, mirror + rotation, invalid key/mode, create→save→reopen, close) **plus** HTTP-level round trips against local mock servers (`s3_transport_round_trips_against_local_mock` — path-style signing, ListObjectsV2 XML parsing, get/put; `webdav_transport_round_trips_against_local_mock` — PROPFIND multistatus parse, collection/self filtering, get/put), bounded-timeout tests, and factory/parser unit tests. S3 additionally has live end-to-end evidence: `remote::tests::s3_transport_round_trips_against_live_s3_server` runs bucket create → put → list → get → delete object → delete bucket against a real local S3-compatible server (MinIO at `B:\Program\s3\minio`, `http://127.0.0.1:9000`, `rustfsadmin`/`rustfsadmin`, path-style) and skips itself when the server is down; the original rustfs local server cannot reach storage readiness on Windows (see `docs/PITFALLS.md`). WebDAV real-provider behavior (e.g. 123pan/Nextcloud) is still code-reviewed only.

### Browser bridge (KeePassHttp)

Split across `src-tauri/src/bridge/{types,crypto,dispatch}.rs` for the pure protocol (request/response types, per-field AES-256-CBC+PKCS7 encryption, verifier, response HMAC, request dispatch) and `src-tauri/src/bridge/server.rs` for the loopback HTTP server, lifecycle (`BridgeState` managed state, started/stopped by `sync_bridge` on startup and every `set_config`), and the associate approval board (`ApprovalBoard` + `bridge_approve` command). The `BridgeHost` trait (implemented by `VaultSession`) isolates session access so the protocol layer is unit-testable without sockets.

- **Transport**: one JSON POST per TCP connection to `127.0.0.1:19455`; headers capped at 16 KiB, body at 1 MiB, read timeout 10 s. The server holds no secrets — a locked vault answers with `{"Success":false,...}` and no auto-unlock.
- **Associate flow**: browser sends `associate`; under the vault mutex the server first rejects a locked vault, malformed 256-bit key, or bad verifier, and captures the stable backend-active `sessionId`. It then registers a one-shot approval token, emits the Tauri event `bridge-associate-request` (payload `AssociateRequest { token, id }`, never key material) to the frontend `BridgeApprovalPrompt` (mounted in `+layout.svelte`), and waits up to 120 s for `bridge_approve` **outside** the vault mutex. The token is removed after allow, deny, or timeout, so a late response cannot revive an expired request. After approval the server reacquires the mutex and registers the key only if the captured session is still backend-active; a tab switch/close rejects the request instead of binding it to another vault. The pending AES key stays in a zeroizing backend-only object throughout the wait. On approval the client gets `{ Id, Key, Hash, Verifier, Success }`; keys are held in the session (`bridge_keys`) and wiped by `close_vault`. Re-associate with a known id refreshes that client's key.
- **Matching and writes**: `get-logins` uses `url_host` host-equal-or-subdomain matching against entry URLs (same rule family as auto-type; the recycle bin subtree is skipped); entries carry `Uuid` (hex), `Login`/`Password`/`Url`/`SubmitUrl` encrypted, `Name`, `Realm` (empty), and `Totp?` when present. `set-login` updates only a referenced entry's changed username/password (the submitted page URL is not allowed to overwrite its canonical URL), creates a KeePass history snapshot for a real change, or creates a new entry titled by the URL host. A real mutation marks the session dirty, and every successful request emits `browser-vault-changed` so the desktop publishes the entry and dirty tab immediately. This mirrors KeePassHttp's `CreateBackup` + `UpdateUI` behavior; it deliberately does not force a database save, so the normal visible save/lock workflow remains authoritative. `get-logins-count` counts matches without payloads. `generate-password` returns a fresh 20-char password (upper/lower/digits/symbols, one per category — mirrors the app's `DEFAULT_DATABASE_SETTINGS.generator`) in the plaintext `Password` response field: it is newly generated for the browser to fill a form, not a vault secret, so it is not field-encrypted (still HMAC-authenticated via the response envelope).
- **`db_hash`**: SHA1 of (root group uuid ‖ recycle-bin group uuid) rendered as 40 lowercase hex chars — it changes whenever the vault structure changes, so browsers re-ask on identity changes.
- **Verifier/HMAC**: per KeePassHttp, the request `Verifier` = AES-256-CBC(key, iv = request nonce bytes) encrypting the base64 string of those nonce bytes — the server decrypts it and compares against `base64(nonce)`. Every response carries a fresh random `Nonce` (used as the AES-CBC IV for its encrypted fields) and `Hmac` = HMAC-SHA256(key, response `Nonce` bytes ‖ response `Verifier` ciphertext bytes); a fresh `Verifier` is likewise derived under the new nonce. Both sides validate accordingly. Tests cover NIST SP 800-38A block 1, RFC 4231 case 2, tamper rejection, and encrypted round-trips (offline; no real-browser E2E evidence in this environment).

Outside Tauri, `services/vault.ts` simulates the same commands on `demo-vault.ts` data persisted to `localStorage`. It is a UI-development surface only and must never be used as evidence for desktop KDBX behavior.

### KeePassRPC bridge (Kee 4.x)

Split across `src-tauri/src/rpc.rs` (pure protocol: SRP-6a math, key-auth challenge/response, AES-256-CBC + SHA-1 MAC frame crypto, v1 JSON-RPC method dispatch) and `src-tauri/src/rpc_server.rs` (loopback WebSocket server on `127.0.0.1:12546`, `RpcState` lifecycle started/stopped by `sync_rpc` on startup and every `set_config`, per-connection handshake state machine). The `RpcHost` trait (implemented by `VaultSession`, keys in `rpc_keys`, wiped on tab close and conditionally retained across the all-tabs lock as described above) isolates session access so the protocol layer is unit-testable without sockets.

- **Transport**: WebSocket upgrade required; valid handshakes to any path other than `/` get 404, non-upgrade HTTP gets the library's 400. Handshake steps use a 30 s read timeout, authenticated connections 300 s idle. Payload cap 1 MiB.
- **SRP-6a setup**: client sends `{protocol:"setup", srp:{stage:"identifyToServer", I, A}}`; the server generates a one-time side-channel password (8 random bytes as 16 lowercase hex chars, 120 s TTL), emits the Tauri event `rpc-side-channel-request` (payload `SideChannelRequest { password, expiresInSecs }` — shown in the desktop UI only via `RpcSideChannelPrompt` in `+layout.svelte`, never logged or persisted) and replies `identifyToClient {s, B, securityLevel}` with `features`. The proof exchange (`proofToServer` M / `proofToClient` M2) follows SRP-6a (1024-bit group); on success the derived session key (K = H(S)) is registered under the client username via `register_rpc_key` and mirrored per-connection. Error envelope codes: `AUTH_FAILED` (wrong password or vault locked), `AUTH_EXPIRED` (side-channel password expired).
- **Stored-key setup** (`key:{username}` → `key:{sc}` → `key:{cc,cr}` → `key:{sr}`): served only while the session key still exists; after lock the key is gone, so the server answers `AUTH_RESTART` and the client clears its stored key and re-SRPs. `cr`/`sr` = SHA-256 over `"1"|secret|sc|cc` / `"0"|secret|sc|cc`.
- **JSON-RPC frames**: `{protocol:"jsonrpc", jsonrpc:{message,iv,hmac}}` with AES-256-CBC (fresh IV) and the protocol's naive MAC `base64(SHA-1(SHA-1(key)||ct||iv))`. Read-only methods (GetAllDatabases, FindLogins, GetPasswordProfiles, GeneratePassword) dispatch under a short `VaultSession` lock. `AddLogin`/`UpdateLogin` instead decode and validate once, capture the backend-active `sessionId`, then run prepare → KDF/serialization/storage persist → complete; only prepare/complete hold the session/registry locks, and all blocking persistence runs outside them. Responses are JSON-RPC 2.0 with numeric `id` echo. Tampered frames or a key wiped by lock close the connection without a reply.
- **Write path** (`AddLogin`/`UpdateLogin`, mirroring KeePassRPC `KeePassRPCService.JSONRPC.cs` + `MergeEntries`/`MergeInNewURLs`): `AddLogin [EntryDTO, parentUUID, dbFileName]` creates an entry (uuid server-generated) under the parent group (empty/unresolvable → root; a parent inside the recycle bin is skipped); `UpdateLogin [EntryDTO, oldLoginUUID, urlMergeMode, dbFileName]` requires non-empty `oldLoginUUID`/`dbFileName` and updates in place with a history snapshot (the plugin's `CreateBackup`), rejecting entries in the recycle bin. Field mapping follows `setPwEntryFromEntry`: first `FFTpassword` → `Password`, all `FFTusername` → `UserName` (last wins), remaining fields → custom strings named `displayName` (fallback `name`); `uRLs[0]` → `URL`, extra URLs space-joined into the same field so the read path sees every URL. URL merging (`merge_urls`) implements all five `urlMergeMode` modes (1 merge-new-first, 2 delete-old-primary-then-merge, 3 keep-old-append-new, 4 unchanged, 5 whole-list replace; unknown → 4); the server offers `KPRPC_FEATURE_ENTRY_URL_REPLACEMENT` so Kee sends mode 5. The prepare phase mutates only a cloned database and pre-generates a stable UUID for adds; a persist failure therefore leaves the live session unchanged. A process-local persistence gate serializes every runtime transaction that writes a vault or local mirror (create, remote open/refresh mirroring, save/re-encrypt/change-key/save-as, remote merge, favicon auto-save and RPC) from prepare through completion without holding the session lock, preventing two successful stale snapshots from overwriting each other on disk. Completion is bound to the captured originating session even after a tab switch. If other in-memory edits arrived meanwhile, the RPC operation is replayed onto the current database and the session stays dirty so both changes reach the next save; for a concurrent edit of the same entry, the later RPC fields win and the UI intermediate state remains in KeePass history. If the originating tab closes or a concurrent delete makes replay impossible after persistence, the protocol still returns the DTO captured from the successfully persisted snapshot rather than reporting a false failure. Responses are the updated entry DTO with an embedded `db` summary. Errors: `-32001` "oldLoginUUID could not be resolved to an existing entry.", `-32002` "Entry is in the Recycle Bin.", `-32600` for the plugin's `ArgumentException` mirrors. (Deviation: extra fields are stored as KDBX strings rather than the plugin's private "KPRPC JSON" config; the update path overwrites fields but does not delete stale custom fields.)
- **Locked vault**: SRP refused (`AUTH_FAILED`), stored keys absent (`AUTH_RESTART`), in-session JSON-RPC closes — the bridge never serves data while locked and never auto-unlocks.
- Offline verification only: protocol state machines are tested with the extension's own `SRPc` math (JS-mirror client) and raw-socket WS handshake/framing smoke tests; no real Kee 4.x E2E evidence exists in this environment.

## Serialization rules

- KDBX entry/group uuids are rendered as hex strings; group UUIDs are stable for the session.
- `password` never enters `VaultState` or the Tauri `VaultEntry` payload; reveal, copy, edit-prefill, CSV export, and the security report resolve entry passwords server-side (`get_entry_password`, `export_csv`, `security_report`). The browser fallback keeps demo passwords in `VaultEntry.password` for its local simulation. Entry passwords never enter config, logs, or error strings.
- Protected custom fields follow the same rule as passwords: their `value` is always empty in the Tauri `VaultEntry` snapshot (only the `protected` flag travels), and reveal/copy/editor-prefill resolve the value server-side via `get_custom_field_value`. The editor fetches protected values on demand before saving and gates the save button until they settle, so saving an edit never overwrites a protected value with an empty string. CSV export and the history payload keep protected values server-side (export is explicit user action; history restore is index-based and never displays the value in the UI).
- `modifiedAt` is refreshed and `revision` incremented on every mutation; mutation snapshots expose the new revision so the renderer can order/merge results and detect stale responses.

## Cross-cutting gates

- Command names, arg names, serde casing (camelCase), error strings, and tests must stay aligned across `invoke` calls and Rust handlers.
- A new mutation requires: Rust handler + test, frontend `vault.ts` method, UI wiring, and this reference update.
